# tickets/ — 規格功能票（開發的唯一工作單位）

> 本資料夾**進版控**，是開發的依據：`/dev` 嚴格遵守「**無票不開發**」——任何會改動程式碼的
> 新功能 / 行為修改，都必須先有一張票（由 `/pm` 與案主確認後開立）。
> 討論過程與 demo 素材放 `cache/`（不進版控）；系統「目前實際行為」以 `docs/SPEC.md` 為準。

## 命名（作者前綴）

`<作者前綴>-<流水號>-<kebab-或中文短題>.md`，例：`AMY-01-掃碼入庫.md`。

- **前綴 = 每個 clone 設定一次**：`git config ticket.prefix AMY`（2~8 個大寫字母或數字、字母開頭；
  存在 `.git/config`，不進版控）。前綴代表「這台 clone 的作者」，**不是**「誰想到需求」。
- 流水號**只在自己的前綴裡遞增**——每個人有獨立的號碼空間，結構上不會撞。
- **同一人平行開第二個 session 也在開票時**，第二個 session 用
  `TICKET_PREFIX=AMY2 make new-ticket …` 指定別名：同一台機器上先後開的票，取號掃得到彼此（見下）；
  但別台機器上還沒推的票、真的同一瞬間取的號掃不到，同前綴照樣撞。
- 建議把**領域**放進短題開頭（例 `AMY-01-庫存-…`）：票號負責唯一性，檔名負責可讀性。
- 專案若有舊制 `<舊制前綴>-XXXX` 票（`scripts/framework-config.sh` 的 `TICKET_PREFIX`，預設 `TK`）
  **不改號、不再發新號**（凍結），lint 兩制並收。
  同名不同義，別搞混：設定檔裡的 `TICKET_PREFIX` 是凍結的舊制前綴；開票時的**環境變數**
  `TICKET_PREFIX` 是「這一次要用的作者前綴」。

> 為什麼用作者前綴而不是全域流水號（源專案 v4.11.0）：撞號是「取號」與「推送」之間的
> 競爭條件——兩個人在對方 push 之前取號，fetch 再勤也看不到彼此（源專案四度因此撞號）。
> 作者前綴讓取號**不需要與任何人協調**。

**開票一律用 `make new-ticket t="短題" r="角色"`**（＝`scripts/new-ticket.sh "<短題>" "<角色>"`），
不要自己挑號碼。它依序做四件事：

1. **讀前綴**：環境變數 `TICKET_PREFIX` 優先，其次 `git config ticket.prefix`；都沒有就停下來、印設定方法。
2. **先問遠端**：`git fetch --all`，**每一條遠端分支**上的票都算——只看整合分支會看不到別人
   feature 分支上剛開的票（源專案 v4.8.0、v4.45.0）。
3. **再掃這台機器上的每一個工作區**（含主目錄）：別條 session 剛開、還沒提交的票 fetch 看不到，
   而開票到推送之間那幾分鐘最容易撞（源專案 v4.55.0、v4.70.0）。只讀檔名，不碰別人工作區的內容。
4. 三邊（遠端、其他工作區、自己這裡）合起來，在**自己的前綴**裡取最大號 +1，照下方模板建檔。
   只認**檔名開頭**的票號：工作區的資料夾名、標題裡提到的別張票號都不算，中文檔名也認得（源專案 v4.94.1）。

- 離線（fetch 失敗）時退回這台機器看得到的最大號並印提醒，push 前務必先 `git pull --rebase`。
- **開完票盡快提交並推上去**：跑過 `make hooks` 的 clone，開發分支 commit 後會自動推；沒跑的自己推。
  別台機器的取號只看得到已經推上去的票；同一台機器上，已提交但沒推、又沒有任何工作區開著那條分支的票，
  取號同樣看不到。
- 兩條 session **同一瞬間**取號沒有鎖，可能拿到同一個號——同一人要同時開票就用上面的別名。
- 撞號的最後防線是 `ticket-lint`：同一個 `id` 出現在兩個檔，或跟 `origin/stage` 上同號卻不同標題，都會紅燈。
  工具本身有自動化測試 `scripts/ticket-tools-test.sh`（`make ticket-lint` 會一起跑）。

## 狀態流（三態）

`待開發` →（/dev 動工時）→ `開發中` →（驗收通過）→ `完成`

- 狀態寫在票的 frontmatter `status`，由誰推進：PM 開票=待開發；/dev 動工=開發中；驗證通過=完成。
- 作廢的票不刪檔，狀態改 `作廢` 並在備註寫原因（留脈絡）。
- 票完成＝程式＋測試完成，而且合流 `stage` 時 `docs/SPEC.md` 已同步（SPEC 只在合流那一次寫，見〈鐵則〉3）。
- 格式與一致性由 `scripts/ticket-lint.sh` 機器檢查（`make ticket-lint`，含在 `make check`；
  專案有 CI 時建議把 `make check` 掛進 CI，票號重複／格式漂移在 push/PR 直接紅燈）。
  查哪些見〈各段怎麼寫、機器查什麼〉。

## 各段怎麼寫、機器查什麼

### ticket-lint 的範圍

`make ticket-lint`（含在 `make check`）。

**每一張票都查，不分新舊：**

- `id` 格式：`<作者前綴>-<兩到四位數字>`（例 `AMY-01`），或舊制 `<舊制前綴>-<四位數字>`；檔名要以 `<id>-` 開頭。
- `status` 是四種之一；`roles`、`title` 有填。
- 完成的票要有 `spec`；`spec` 有填就要指向存在的檔案（只看 `#` 前面的路徑）。
- `depends` 有寫就要是 `[AMY-03, BOB-12]` 這種格式（沒有寫 `[]`），而且不能包含自己；沒寫這個欄位的舊票不查。
- frontmatter 同一個欄位出現兩次（多半是合併沒接好；源專案 v4.45.0）。
- 同一個 `id` 出現在兩個檔。
- **跟 `origin/stage` 撞號**：同一個 `id`、標題卻不同（兩邊各開了一張同號的票）。同一個檔改標題不算；
  兩邊分歧之前就有的號不算；取不到 `origin/stage`（還沒設遠端、離線）會印一行說跳過這項比對。

**只提醒、不擋：** 開發中沒填 `owner`；同一張票裡有重複的 `##`／`###` 標題（多半是合併把同一段留了兩份）。

**三條新規則**（〈這次可能會弄壞什麼〉〈條件確認〉〈數字口徑〉）只查**同時**符合下面三件事的票：

1. 狀態是 `開發中` 或 `完成`。`待開發` 不查——剛開的票原樣跑 lint 會過；標成開發中的那一刻起，
   〈條件確認〉的範例列沒換掉就會紅。
2. `created` 在生效日當天或之後（見〈新規則從哪一天的票開始套用〉）。
3. 這次有改到：跟 `origin/stage` 比有差異、還沒提交、或還沒加進版控的票檔。
   取不到 `origin/stage` 時改成查全部符合前兩項的票。

`ticket-lint` **不檢查**〈逼問紀錄〉與「欄位權限：」那一行的內容——那兩處是寫給看票的人（規格審查、驗收）看的。

### 逼問紀錄

開票前 grill 問過什麼（源專案 v4.76.0）。一題一行：**問了什麼／對方怎麼答／因此推翻或確認了哪個假設**。
看票的人不用翻對話，就知道開工前確認過哪些事。框架票、只修錯字這類沒有要問的，寫「不適用：<理由>」。

### 欄位權限

〈需求細節〉固定有一行「欄位權限：」（源專案 v5.37.0），寫法照 `AGENTS.md`〈沒權限的欄位，哪裡都不出現〉：
這張票讓哪些欄位出現在新地方、或開給新角色，每一欄寫「原本哪些角色看得到 → 做完哪些角色看得到」。
兩種情況可以用固定寫法、不必逐欄答：

- 沒有任何欄位出現在新地方或開給新角色（例：只把某一欄從列表拿掉）→
  「欄位權限：沒有欄位出現在新地方或開給新角色（這張票改了〈什麼〉）」
- 不改程式，也不改開給誰（例：只改流程、文件、CI）→
  「欄位權限：不涉及（不改程式、不改開放對象）」

**全新的東西開票前先問人**（源專案 v5.42.0）：票會做出新的頁面、新的區塊，或站上還沒有同一種資料的新欄位時，
開票前一定要問清楚**誰看得到、誰看不到、誰能改**（開票必問的第五件事，問法見 `pm` skill）——沒問到不開票。
答案寫進〈逼問紀錄〉；「欄位權限：」照答案寫，全新的資料「原本誰看得到」寫「新的，原本沒有」；
下一行固定再寫一行「誰能改：……」。

### 條件確認

（源專案 v5.5.0、v5.27.0、v5.41.0）

**什麼要進這張表**：開票的 agent **自己加的、案主沒講過**，而且會讓資料「出現／消失／被一次改掉／被擋掉」的條件，一條一列：

- 出現條件、可見性（某個區塊要符合什麼才出現、誰看得到）；
- 預設的篩選、排序、預設值；
- 回填、一次改掉一批舊資料；
- 驗證擋送出、擋儲存。

純文字、版面、顏色這類沒有筆數的不進表（照預設做，寫在〈需求細節〉）；案主親口講過的規則也不進表。

**怎麼填**

| 欄 | 寫什麼 |
|---|---|
| 條件（含分母） | 用白話一句講這條規則，並講清楚分母：哪一群資料、共幾筆 |
| 符合／擋掉 | 開票時**唯讀查正式環境**的筆數，寫「N 筆」。查不到寫「查不到：<原因>」，不拿別的環境或估的數字代替 |
| 狀態 | `已確認`｜`未確認`｜`待 prod 資料`，只能是這三種 |
| 回答日 | `YYYY-MM-DD`；「已確認」與「待 prod 資料」必填 |

- **未確認**：一律先寫這個。案主回「不同意」（照對方的改法改票、重查筆數）、「先略過」「我看不懂」，或還沒問，都是未確認。
- **已確認**：案主在勾選清單回「同意」才算，回答日填那天。
- **待 prod 資料**：只給「要看到正式環境的筆數才答得出來、而筆數現在查不到」的列——〈符合〉或〈擋掉〉以「查不到：」開頭，
  案主在推 `stage` 前那則清單親自選「等 prod 筆數再答」才能標，回答日填那天。
  規則本身（誰可以、誰不行、算不算）不需要筆數就答得出來的，不能標。推 `prod` 前還是要重查筆數再問。
- 這一節沒有條件可列：整節改寫成「不適用：<理由>」（理由至少兩個字）。

清單怎麼產生、怎麼問、回答之後怎麼改票，見 `pm` skill〈4b〉；清單範本是 `.agents/skills/pm/condition-checklist.html`。

**機器什麼時候要求這一節**：票的內文或標題出現下面任何一個詞，就一定要有〈條件確認〉節
（HTML 註解與 frontmatter 裡的不算）：

> 出現條件、可見性、回填、篩選、才會出現、才會顯示、才顯示、才出現、擋下、擋掉

**機器擋什麼、什麼時候擋**

| 時機 | 擋什麼 |
|---|---|
| `make ticket-lint` | 有上面那類字卻沒有這一節；這一節格式壞掉——表頭缺欄、範例列（條件以「（例）」開頭）沒換掉、〈符合〉〈擋掉〉空白、狀態不是三種之一、「已確認」沒有回答日、「待 prod 資料」沒有「查不到：」或沒有回答日、沒有表格也沒寫不適用、「不適用」沒寫理由。**「未確認」不擋**——開發中不等回答。 |
| 推 `stage` 前的條件確認檢查（`make confirm-lint` 可先查） | 這次要進 `stage` 的票（狀態開發中或完成）裡，狀態不是「已確認」的列；有那類字卻沒有這一節的票。唯一例外：格式合格的「待 prod 資料」放行，並印一行提醒。 |
| 要上 `prod` 的票（`bash scripts/unconfirmed-conditions.sh <票號…>`） | 同上，但**「待 prod 資料」也算沒確認**——這時筆數查得到了，重查再問。 |

- `make confirm-lint` 查目前這條分支；`make confirm-lint ref="feature/AMY-12 feature/AMY-13"` 一次查好幾條。
  它查的是「這條分支還沒進 `stage` 的那一段」改到的票，讀的是**已經提交**的版本——改完票要先 commit。
- 啟用 git hooks（`make hooks`）的 clone，推 `stage` 時會自動跑同一道檢查。
- 批次合流時卡在別人的票：請那張票的負責人去問、去補，不要替他改狀態。
- **擋的是忘記，擋不住亂填**：筆數有沒有真的查過、分母對不對、條件有沒有漏列、「不適用」的理由成不成立，
  機器看不出來；一個那類字都沒出現的票也不會被要求。這些靠 `pm` skill〈4b〉與看票的人。
- 舊票不回頭補：見〈新規則從哪一天的票開始套用〉。

### 數字口徑

（源專案 v5.19.0）票新增或改變一個**顯示給人看的數字**（儀表板、報表、匯出、統計卡、筆數徽章、比例）時，
加一節 `## 數字口徑`，每個數字一列：

```markdown
## 數字口徑

| 數字 | 期間與時間欄位 | 時區 | 算哪些（含不含取消、作廢、測試資料） | 同一筆算幾次 | 加總／平均／比例（分母） | 空值 | 跟站上哪個數字同口徑，或差在哪 | 狀態 | 回答日 |
|---|---|---|---|---|---|---|---|---|---|
| 準時出貨率 | 出貨日落在所選月份 | 門市所在時區 | 不含已取消的訂單、不含測試資料 | 一張訂單算一次 | 比例：準時出貨數 ÷ 出貨數 | 沒有出貨日的不算 | 分母跟首頁「本月出貨數」同一個口徑 | 未確認 | |
```

- 第一欄一定叫「數字」，並且要有「狀態」「回答日」兩欄；其他欄照上面的表頭。
- 狀態只有 `已確認`、`未確認` 兩種：案主講過的口徑寫「已確認」＋講的那天；agent 自己決定的寫「未確認」。
  「已確認」要有回答日。
- 沒有新的或改變的數字卻被要求這一節：整節寫「不適用：<理由>」（理由至少兩個字）。
- **不要預先放空標題**——模板裡沒有這一節就是這個原因：預放了，每張票都會多一段沒人填的表。
- 不放進條件勾選清單：口徑另外問，一個數字一題。開發中不等回答，推 `stage` 前一定問完；
  口徑**沒有**「等 prod 筆數再答」的例外。

**機器什麼時候要求這一節**：票的內文或標題出現下面任何一個詞（HTML 註解與 frontmatter 裡的不算）：

> 儀表板、統計卡、成功率、比例、比率、平均、總數、KPI

擋的內容跟〈條件確認〉同型：`make ticket-lint` 擋「有那類字卻沒有這一節」與格式壞掉（表頭不對、範例列沒換掉、
狀態不是兩種之一、「已確認」沒有回答日、「不適用」沒寫理由）；推 `stage` 前與要上 `prod` 時擋「不是已確認」。

專案有自己的數字講法（例如某個專有的比率名稱）要加進清單：`scripts/ticket-lint.sh` 與
`scripts/unconfirmed-conditions.sh` 裡的 `NUM_TRIGGER_RE` **兩支一起改**，`scripts/ticket-tools-test.sh`
裡逐個字樣驗證的那份清單也一起加——那支測試會比對兩邊一不一樣。

### 這次可能會弄壞什麼與走查紀錄

（W 編號，源專案 v5.30.0；合流前先查的 `make walkthrough-lint`：源專案 v5.39.0）

**動工前寫計畫**。〈這次可能會弄壞什麼〉一行一個編號（`W1`、`W2`…）：

- 這次改動有機會波及、但**不打算改**的頁面或功能；
- 需求要求「其他頁也要檢查或修」的（不論寫成一併、同款、也要、一起），**一頁一個編號**。

每個 W 在〈驗收標準〉（或標題以「走查」開頭的節）要有一行**以同一個編號開頭**，寫那一頁要按哪幾個互動。
真的沒有：整節寫「不適用：<理由>」。

**推 `stage` 前寫結果**。每個 W 都要在〈開發備註〉（或〈走查〉節）交代走過了、還是沒走。走過的寫一行：

```markdown
- 走查（真人眼看）W1 訂單清單頁、W2 訂單明細頁：下拉選單各選一次，選項完整
```

沒走成的，照 `user-walkthrough`〈跳過之後怎麼做〉的三行寫：

```markdown
⚠️ 走查未完成
· 沒走的是：W2 訂單明細頁
· 為什麼：  <卡在哪一步、看到什麼現象、為何判斷與本票無關>
· 誰該補走：<誰、什麼時候>
```

- 走過的那一行要以「走查（真人眼看）」「走查（HTTP 腳本）」或「走查（HTML 檢查）」開頭，W 編號寫在**同一行**。
  版面類的 W 用真人眼看——HTML 檢查看不到版面。
- 沒走的，W 編號寫在「沒走的是：」那一行。寫了「沒走」的，交付時要在訊息開頭講出來。
- 編號整段比對：寫了 `W10` 不會讓 `W1` 算成已交代。
- 批次合流時卡在別人的票：請那張票的負責人補，不要替他寫「沒走」。

| 時機 | 擋什麼 |
|---|---|
| `make ticket-lint` | 沒有〈這次可能會弄壞什麼〉這一節；這一節是空的；有哪一行沒有編號；哪個 W 沒有對應的驗收／走查行 |
| 推 `stage` 前的走查紀錄檢查（`make walkthrough-lint` 可先查，`ref=` 用法同 `make confirm-lint`） | 這次要進 `stage` 的票（狀態開發中或完成）裡，哪個 W 既沒有「走查（…）」那一行、也沒有「沒走的是：」那一行。讀的是已經提交的版本 |

> 由來（源專案）：一張票的邊界寫了「不動隔壁那個畫面」，驗收標準卻沒有一條關於它，幾天後那個畫面的互動
> 在整合環境壞了一整天；另一張票寫了「另外兩頁的同款元件一併檢查」，W1 只是為了過 lint 補的一行，
> 一頁都沒走就合進了 `stage`。所以分兩道：`ticket-lint` 管**計畫**（W 有對應的驗收行），
> 走查紀錄檢查管**結果**（走過沒有）。

### 新規則從哪一天的票開始套用

下面這幾項只查 `created` 在 **`TICKET_RULES_SINCE` 當天或之後**的票：`ticket-lint` 對上面三節
（〈這次可能會弄壞什麼〉〈條件確認〉〈數字口徑〉）的檢查、推 `stage` 前的走查紀錄檢查，
以及條件確認檢查裡「有那類字卻沒有這一節」那一條。
票裡**已經有**〈條件確認〉〈數字口徑〉的表、而列的狀態不是「已確認」的，條件確認檢查不分新舊照擋——表都寫了，就要問完。
這個日期設在 `scripts/framework-config.sh`：

- **新專案**：保持預設（`2000-01-01`）＝所有票都套用。留空也是全部套用（連沒填 `created` 的票也查）。
- **從舊版框架升級的專案**：改成升級當天的日期——舊票沒有這些段落，不改的話舊票一被改到（例如標成完成）就會紅，
  取不到 `origin/stage` 時更是整批紅。舊票不用回頭補。
- 格式是 `YYYY-MM-DD`；寫成別的 `ticket-lint` 會紅，並且當成全部套用。
- 有設日期時，沒填 `created` 的票不查。
- 臨時要換一個日期跑（補查、測試）：環境變數 `TICKET_RULES_SINCE=…` 會蓋過設定檔。

機器讀的是票自己寫的 `created`，把日期改舊就躲得掉——**這幾道擋的是忘記，不是存心**。

## 多 session 平行協作（領票制）

同一個 repo 可能有多個 session / 多台機器同時開發，協作以「票」為鎖：

1. **動工＝領票**：把票標 `開發中` 的同時填 `owner`（自己的代號，例：amy-mac、cloud-a）。
2. **他人的票不碰**：看到 `開發中` 且 owner 不是自己 → 不改該票範圍的程式；要接手先問使用者、改 owner。
3. **一 session 一工作區（必須，源專案 v4.14.0）**：開發一律在自己的隔離工作區做，主目錄只做合流
   （merge／push／盯部署），不在主目錄開發、不在主目錄 `checkout -b`。開工第一件事：

   ```bash
   make worktree n=AMY-12      # → .claude/worktrees/AMY-12/，分支 feature/AMY-12
   ```

   它從最新的 `origin/stage` 開分支（票的 `depends` 有還沒進 `stage` 的票是例外，見〈相依的票〉），
   並把 `scripts/framework-config.sh` 的 `WORKTREE_COPY_GLOBS` 列的本機檔案（不進版控、少了檢查就會紅的那些）
   一併帶過去。收工 `make worktree-clean n=AMY-12`；看現況 `make worktree-list`。
   **工作區內不要 checkout `stage`**——`stage` 一被佔住，主目錄就切不回去，別條 session 也不能合流。
4. **一次要開發多張票：先分組**（源專案 v5.25.0）。同一條線的放同一棵工作區，其餘各開一條 session；
   同一個 session 同時只在一棵工作區開發，不預先開好幾棵。怎麼分見 `pm` skill〈4-2. 一次開發兩張以上〉。
   同一條線的做法：工作區用這條線**第一張**的票號開（不用併名），票用
   `make ticket-handoff to=AMY-12 t="AMY-12 AMY-13"` 搬進去——它會順手領票（待開發改開發中、owner 空白才填
   `claude-cc-<工作區名稱>`；源專案 v4.81.0）。每張票的〈開發備註〉寫一行「同一條線，在 AMY-12 的分支上做」。
5. push 前先同步遠端由 git-sync-gate hook 強制。

## 相依的票（`depends`）

（源專案 v5.16.0）B 票要用到 A 票的程式（資料表、API、畫面）才做得出來／測得了時，B 的 `depends` 寫 A：
一張寫 `depends: [AMY-03]`，兩張以上寫 `depends: [AMY-03, BOB-12]`，沒有就寫 `depends: []`。

- PM 開票時知道就填，dev 開工時發現就補；只是「主題相關」不算。
- `ticket-lint` 只擋格式與「不能是自己」，**不查 A 的票檔存不存在**（不同分支上的 `tickets/` 不一定一樣齊），
  所以 A 在哪條分支、有沒有進 `stage`，由開工的人照下面的步驟判斷。
- **不要叫使用者「等 A 先上 stage」**——票做完常常先停在 feature 分支、累積幾張再一起合流，
  等 A 上 `stage` 可能要等好幾天。

開工前讀 B 的 `depends`，先 `git fetch`（A 剛推的分支與新提交才看得到），再對每一張 A：

1. **找 A 的程式在哪條分支**：

   ```bash
   git branch -r --list 'origin/feature/<A>' 'origin/feature/<A>-*'
   ```

   沒有就看 A 的票 `owner`（`claude-cc-<名稱>` → `origin/feature/<名稱>`），再沒有就讀 A 的〈開發備註〉。
   找到好幾條、或都找不到 → 讀 A 的〈開發備註〉，判不出來就問使用者。**找不到分支不等於 A 還沒開工。**

2. **A 有沒有還沒進 `stage` 的程式**：

   ```bash
   git log --oneline --no-merges --cherry-pick --right-only origin/stage...origin/<A 的分支> -- . ':!tickets'
   ```

   （`--cherry-pick`：內容已經直接進 `stage` 的不算；`':!tickets'`：只動票檔的提交不算程式。）

   - **有** → 從 A 的分支開：`make worktree n=<B 的票號> base=origin/feature/<A 的票號>`。
     B 的〈開發備註〉寫一行「基底 <A 的分支>（<sha>），併 stage 要跟 A 一起、A 先併」。
     兩張以上的相依票都還沒進 `stage` → 從其中一張的分支開，其他的 `git merge` 進來。
   - **沒有，而且 A 的票是「完成」或 A 的程式已經在 `stage` 上** → 照平常從 `stage` 開。
   - **沒有，A 也還沒寫程式**（票是待開發，或分支上只有票）→ 先不開 B，
     跟使用者說「B 要等 A 把資料表定下來，或兩張排同一條線做」。

3. **B 疊在 A 上時，跑檢查之前先 `git merge origin/<A 的分支>`**，把 A 最新的拿進來——
   合起來的版本才是跑過檢查的版本。

4. **併 B 進 `stage` 之前，看這條分支會帶上哪幾張票**：

   ```bash
   python3 scripts/branch_tickets.py <B 的分支> <B 的票號…>
   ```

   （它不 fetch，先自己 `git fetch`；有別張票時結束碼是 1。）對標成「別張票」的每一張：

   - 那張票已「完成」**而且**那幾筆內容已經在 `stage`（例：`git log origin/stage --grep <那張票號>` 看得到對應的提交），
     或只是提交標題裡提到 → 回報時講一句，不用再問。票只是標「完成」、程式還沒進 `stage` 的不算，照最後一點處理。
   - 那張是同一條線做的（B 的〈開發備註〉或那張票寫了在 B 的分支上做）→ 當成 B 的一部分，回報時講一句。
     **例外**：使用者只同意其中幾張時，停下來問，不把沒同意的票一起併。
   - 那張是還沒進 `stage` 的另一條分支（B 疊在它上面）→ 那張也要使用者這次同意、同一批、**先併**；
     那張被退件或作廢 → B 不能單獨併，停下來問。

   開場簡報的〈平行現場〉也會在「N 個 commit 還沒進 stage」那一行標出「含別張票的提交」
   （分支名撈得到票號的才判斷；沒寫票號的提交認不出是誰的，只列不算）。

A 的分支還沒推上遠端時，`base=` 改用本機的分支名（`base=feature/<A 的票號>`），或請那條 session 先推上去。

## 鐵則

1. **角色與目的必填**：`roles` 與「目的」沒確認前不開票（防止假設角色導致重構）。
2. **一票一個垂直功能**：太大就拆票。
3. **SPEC 只在合流 `stage` 那一次寫**：開票與 feature 分支上不動 `docs/SPEC.md`，也不為還沒上 `stage` 的功能
   新增「⏳ 未開始」列——規劃資訊住在票裡。合流的同一次，依票的〈開發備註〉把這張票的變更寫進 SPEC、
   在變更歷史留一列。完成的票 `spec` 必填（`ticket-lint` 會擋）。
4. **自己加的條件要附筆數、讓案主一次勾完**（源專案 v5.5.0）：agent 開票時自己加、會讓資料
   出現／消失／被一次改掉／被擋掉的條件，逐條填進〈條件確認〉表（符合幾筆、擋掉幾筆、分母是什麼）。
   開發中不等清單的回答；但表裡還有「未確認」就**不能推 `stage`**（源專案 v5.41.0）。
   機器只擋「出現這類字樣卻沒有這一節」「這一節格式壞掉」「推送時還有沒確認的」——**擋的是忘記，擋不住亂填**。

   > 由來（源專案）：agent 自己加了「至少要有一份附件，那個區塊才出現」這類條件，寫進票裡、案主也點頭了，
   > 卻沒有人看過筆數——上線後才發現正式環境絕大多數的真實資料都被擋在外面。
