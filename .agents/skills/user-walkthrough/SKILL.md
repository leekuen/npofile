# 真人操作走查（user-walkthrough）

> **為什麼有這份 skill**：源專案連續多張票在 `run-checks` 全綠、單元測試全過之後，
> 一交到案主手上就被打回——按鈕按了沒反應、功能存在但找不到入口、
> 訊息收到了畫面卻永遠顯示「傳送中」、指定密碼後行為與拍板相反。
> 共同根因：**測試驗的是零件，案主用的是過程。** 每個零件都對，組起來的體驗卻是壞的。
> 這份 skill 把「案主會做的事」變成出貨前的固定關卡——**預設走縮小走查**（源專案 v4.26.0）。

## 何時用（強制）

任何票只要改動**使用者看得到或按得到**的東西——畫面、按鈕、表單、訊息、狀態顯示、
流程順序——在 `run-checks` 綠燈之後、**回報案主之前**，必須走本清單。
純後端重構、純文件、純 CI 改動可跳過，但要在回報裡說明為什麼跳過。
**例外：後端改動讓送出的回應欄位被拿掉或改掉、或拿掉端點或動作，不算純後端**（定義見第四題）——一律先過下面的第四題
（源專案有一張票把某個清單 API 的電話欄位拿掉，只跑腳本，詳情頁畫的正是清單那一筆，所有人都看不到電話）。

### 第四題：關鍵使用流程（源專案 v5.3.0）

第四題（題目見下面〈先問四題〉）為「是」，走查就**不是**只走改動點，而是把受影響角色的**關鍵使用流程**從頭到尾**實走一次**：

1. **先查誰在讀、再列流程**：動工前 grep 欄位名（拿掉的是端點或動作就 grep 它的路徑與名稱）。
   grep 範圍是**整個產品程式**（`scripts/framework-config.sh` 的 `PRODUCT_DIRS` 列的每個目錄），
   加上 repo 裡其他會讀它的地方：伺服器端範本與範本裡內嵌的 script、推播或通知的資料讀取、自動化流程的設定檔。
   **不管自己認為有沒有人在讀，都要先查**，不限畫面與資料讀取層。
   **每個讀取的畫面都要追到它的資料來源（資料讀取層 → 端點）**，間接讀取也算（例：清單的那一筆被詳情頁拿來畫，上面那張票就漏在這裡）。
   命中在型別、helper、util 的，要往上追到呼叫它的畫面；只命中註解、測試 mock、示範／教學模式的假後端的，不算讀取方。
   **使用者手上可能還是舊版的客戶端**（要使用者更新或重開才換上的 App、桌面程式）：另對最近一次發到使用者手上那一版的 commit
   跑一次 `git grep <欄位> <sha> -- <客戶端目錄>`，查得到也算讀取方。
   **grep 之後確實沒有任何讀取方**（只有 repo 外的服務在用；repo 內有讀取方的不算）：這一題記為**「否」**，
   回報寫「第四題：否，欄位被拿掉但 grep 無讀取方」，附**完整的 grep 指令與輸出**（只附輸出不算）；有 repo 外服務在用的，寫出它的名稱並
   列進〈回報格式〉的「只有你實機才驗得到的」；repo 內外都沒人讀的，只要寫明「grep 與 repo 外都查無讀取方」；級別照其餘三題與獨立觸發定；不能不查就這樣寫。
   每個讀取的畫面對應一條「使用者拿它完成一件事」的流程（例：打開清單 → 點進一筆 → 看到電話 → 撥出去 → 回報結果）。
   **非畫面的讀取方**（推播、通知、內部 API、自動化流程）：用後端**真的組出來的**資料跑一次，回報寫明資料從哪裡來——
   手寫的資料不算，欄位被拿掉時手寫那份照樣有；驗不到的列進「只有你實機才驗得到的」，不要改用 HTTP 腳本蒙混。
2. **動工前宣告**（源專案 v5.4.0；grep 完就要做；範圍比第四題寬，第四題為「否」也要宣告；**不另外定義「重大變更」**——大小事先劃不出線，上面那張票只動一行卻影響最大）：
   只要這張票會**拿掉、搬走、改掉**現有的東西（不論哪一層），就在**狀態文字**宣告一次，四件事：
   ① 拿掉／改掉什麼；② grep 查到幾個讀取方（附指令與輸出）；③ 要走幾條流程、估幾分鐘（源專案的初估是每條 5～15 分＋備走查假資料，**這是猜的**，頭幾張票實際記時間後回頭修這個數字）；④ 建議跑或不跑＋理由（「跑」＝跑第四題的關鍵流程；走查級別仍照四題定，宣告不改變級別。第四題為「否」＝沒有第四題流程可跑，④ 寫「不跑第四題流程（第四題否），走查照四題定的級別」，不受下面「不跑只能是」限制）。
   建議「不跑」的理由**只能是**：grep 查無讀取方（附輸出）、或同一個 session 在這次改動之後已走過同一條流程；不能是「我覺得沒人讀」。
   **宣告完繼續做，不用 `AskUserQuestion` 卡住**；案主沒回＝跑。第四題明確為「是」（grep 有讀取方）→ 直接跑、宣告裡告知估時，不問；只有灰色地帶才問案主（照樣不等；沒回＝跑）。
   案主說「這次不跑」＝放行，**只管這一次**。
3. **逐條實走真畫面**（瀏覽器或裝置上真的點；走連整合環境的那一型時照〈走 ② 要配兩道護欄〉，不按不可逆的動作——流程裡有送出這類步驟，就在 ① 本機走完整條；**不要用示範／教學模式當實走**，它的假後端自己組欄位），**不能只跑 HTTP／API 腳本**——腳本只證明後端回了什麼，
   證明不了畫面有沒有把它畫出來；前端的測試多半用假資料，欄位被拿掉也不會變紅。走不了照〈先問：這張票准不准跳〉。
4. **走到使用者做完那件事為止**，不是走到改動點為止；改動點之前與之後的步驟都要看（拿掉欄位的症狀常出現在下一步）。
   欄位有條件出現時（例：某欄只有今天、明天的資料才有），每條流程至少走一筆**應該看得到**的資料；條件本身有改，看不到的那一種也要走。
5. **回報寫明**（寫在〈回報格式〉的「關鍵流程」欄）。漏列一個讀取它的畫面，就是這一題沒做完。

### 預設檔位是「縮小走查」，不是全清單（源專案 v4.26.0）

**改的是預設深度，不是走不走。** 舊版的縮小走查要同時滿足「三題全否」**且**
「只動單一畫面的呈現」，於是三題全否、但改動不只一個畫面的票——多半是低風險的——
會直接掉進全清單，一次 10～30 分鐘。

- **四題全「否」→ 縮小走查**（不再要求「且只動單一畫面」）。
- **全清單的觸發條件**：四題任一「是」（源專案 v5.3.0 起多一題），**或**跨介面（同一個變更動到兩個以上的介面）、
  新資料模型、新流程——後面那三個是**各自獨立的觸發**，不受四題管轄。
- 三條防後門規則（不確定往上一級／降級要留痕／案主退過的下次一律全清單）原封不動。

### 開工時就在狀態文字宣告要走哪一級

動工的那一刻就在**狀態文字**（進行中顯示的那行）寫明級別與依據，例如：

    實作 TK-12 清單篩選｜縮小走查（四題全否）

**為什麼是開工不是回報**：寫在回報裡，案主覺得走得不夠時工已經做完了；
寫在開工的狀態文字裡，他一看到就能當場提醒、要求升成全清單、或說這張不用走，**攔截點提前一整輪**。

- **宣告完就繼續做，不等回覆。不要用 `AskUserQuestion` 卡住流程。**
- 會拿掉、搬走、改掉現有東西的票，宣告多四件事（拿掉什麼、讀取方、估時、跑不跑），見第四題步驟 2。
- 回報時仍要寫用了哪一級、依據哪一題（見〈回報格式〉）。
- 純後端／純文件／純 CI 連宣告都不必（本來就沒有畫面可走）；**例外：只要票會拿掉、搬走、改掉現有的東西，一律要宣告（包含 grep 無讀取方的），見第四題步驟 2**；其中後端送出的回應欄位被拿掉或改掉、或拿掉端點或動作的，另要過第四題（grep 無讀取方並附結果的記為「否」）。
- 判準沿用 `AGENTS.md`〈分支與出貨流程〉第 3 步的既有定義（**畫面、文案、流程、狀態**），
  再加上第四題；不另造別的。

## 走多少：依風險分三級（源專案 v4.15.0 判準，v4.26.0 調整預設檔位）

走查是**人工**的，是每張票最貴的一段。但它擋掉的是 `run-checks` 全綠也擋不住的
那類事故（源專案一次 10 分鐘的走查，抓到三個上千條測試全綠卻仍然壞掉的畫面層錯），
所以不能省——**能調的是深度，不是有無**。

**先問四題**（任何一題「是」→ 全清單，不可降級）：

1. 改到**誰能做什麼**嗎？（權限、可見性、角色差異）
2. 改到**狀態怎麼變**嗎？（狀態機、流程順序、背景任務、輪詢、並發）
3. 改到**錢或收不回來的動作**嗎？（金額、送出、刪除、對外通知）
4. **回應欄位或功能被拿掉**嗎？——後端送出的資料（API 回應、推播或通知的資料、送給外部服務的內容），原本會出現的欄位，
   之後少了、改名了、值被清成空字串或 null、值的型別／格式／意義改掉（例：數字 id 變字串、電話改成遮罩、日期格式、選項值改名、欄位搬到別層）、或某些情況（只在清單、只在某些條件下）不再出現；
   或後端拿掉一個端點或動作，呼叫會被拒或找不到（這時回應可能完全沒變）。
   **只算收緊的方向**（原本不給、之後有條件給，不算）。伺服器端範本自己用的變數被拿掉，一樣 grep 範本並附結果；有命中的，至少走那個畫面一次（縮小走查即可），因為不少範本引擎找不到變數時靜默印空白。

| 級別 | 適用 | 走查範圍 |
|---|---|---|
| **免走查** | 沒有任何使用者看得到／按得到的東西改變：純後端重構、純文件、純 CI／框架、只補測試（**第四題為「是」的不算（後端送出的回應欄位被拿掉或改掉、或拿掉端點或動作）；grep 無讀取方並附結果的除外，見第四題**） | 不走，但**在回報寫明為什麼跳過** |
| **縮小走查**（**預設檔位**，源專案 v4.26.0） | 四題全「否」、且不是下一列的三種——**不再要求「且只動單一畫面」** | **A 入口**與 **F 對照拍板**照做，B～E 只走改動點的**前一步 → 改動點 → 後一步** |
| **全清單** | 四題任一「是」，或跨介面、新資料模型、新流程 | A～F 全走，一步不跳 |

**三條防止分級變成後門的規則**：

- **不確定就往上一級。** 判斷不出來屬於哪一級，就是全清單。
- **回報要寫用了哪一級、依據哪一題**——降級要留痕，不能默默少走。
- **案主退過的功能，下一次一律全清單**，不管這次改動多小。退過一次代表那裡的
  隱藏狀態比看起來多（源專案同一張票被退兩次就是這樣）。

## 走不了就跳過，不要停在那裡（源專案 v4.23.0）

走查卡住的原因**多半不在票裡**：裝置或模擬環境不吃點擊、本機環境沒有走得通的資料、
第三方服務沒開、帳號登不進去、憑證還沒上傳。這些是**環境問題，不是這次改動的問題**，
而排除它們常常比開發本身還久——停在那裡修，票就卡住了。
**跳過本身不危險，危險的是案主不知道。**

### 先問：這張票准不准跳（源專案 v4.37.0）

**四題（權限／狀態流程／金錢或不可逆／回應欄位或功能被拿掉）任一為「是」→ 不可跳過。**
走不了就是**阻塞回報**，不是跳過：票停在那裡等人處理，不要當成走完出貨。

用的是升全清單那組判準，**不另立名單**——所以案主不必每次特別交代「這張不准跳」，
也不會有「忘了講就被跳掉」。四題全否的票才適用下面的「試一輪就停」。

> 為什麼是這四題：前三題是「跳過一次 ≈ 出一次貨帶著使用者看得到的缺陷」代價最高的地方。
> 權限看錯讓人看到不該看的、狀態流程斷掉讓單子卡死、金錢與不可逆按下去收不回來——
> 這三種都不是「下次補走就好」。第四題補的是另一種：拿掉欄位時，**沒有人知道還有誰在讀它**——
> 源專案那張拿掉電話欄位的票，當時走查只跑了 HTTP 腳本、沒實走詳情頁，所有人都看不到電話。

### 卡在登入：先請人代登入，再考慮跳過（源專案 v4.69.0）

走查最常見的卡點是**登入要打密碼，而 agent 不代打密碼**。這不是死路：
**先把要走的畫面停在登入頁，請案主（或手上有測試帳號的人）代為登入**，給他測試帳號就好，
登入後由 agent 接手走完。登入狀態保存在裝置或瀏覽器裡的，之後重開不必再登入。

- **四題任一為「是」的票，這一步是必做的**——不問就直接回報阻塞，等於把能走的路當成死路。
- 四題全否的票也先問一句，但**問完不等回覆**，其他部分照做；他回了就回頭補走，
  沒回就照下面的規則跳過並大聲回報（不違反「不要停在那」）。
- 有不用打密碼就能登入的做法（例：瀏覽器裡放好一份測試用的登入狀態），先用那個，不必麻煩別人。
  登進去之後**真的在畫面上點**＝「真人眼看」；只拿登入狀態打端點＝「HTTP 腳本」（見〈憑據型態〉）。

> 案例（源專案）：連續幾張票的走查都因為「要打密碼」而跳過；
> 後來改成先請人代登入，走查當場跑通，抓到一個整合環境上既有、使用者會卡住的真 bug
> （編輯畫面的「取消」壓在狀態列下按不到）。

### 跳過之後怎麼做

- **試一輪就停**：卡住時做**一次**合理的排除（換個入口、重開、換一組資料、換個裝置），
  不成就跳過。不要對同一件事連續重試，也不要為了走查去修環境。
- **跳過之後票照常做完**：`run-checks`、commit 都照走（SPEC 照常在合流 `stage` 那一次寫），不要停在那裡等環境。
- **回報要吵，不要安靜（源專案 v4.37.0）**——放在交付訊息**開頭附近**，
  不是藏在末尾一句話。標題＋固定三行，缺一行等於沒講：

  ```
  ⚠️ 走查未完成
  · 沒走的是：W…（哪一段路／哪幾條驗收標準）
  · 為什麼：…（卡在哪一步、看到什麼現象、為何判斷與本票無關）
  · 誰該補走：…（案主實機／下一個接手的人／合流後由 agent 走 ②）
  ```

  同一段話寫進票的〈開發備註〉，下一個人才知道那裡還沒被看過。

  **格式要與〈憑據型態〉並存、不要另立一套**：走查過的寫
  「走查（真人眼看）」「走查（HTTP 腳本）」「走查（HTML 檢查）」，**沒走查的走上面這三行**。
  一張票兩種都有就兩種都寫。
- **每個 W 編號都要點名**（源專案 v5.30.0）：票〈這次可能會弄壞什麼〉的每個 W，在〈開發備註〉（或〈走查〉節）
  要嘛寫在「走查（…）」開頭的那一行（例：`走查（真人眼看）W1 訂單清單頁、W2 訂單明細頁：…`），要嘛寫在「沒走的是：」那一行。
  推 `stage` 時 pre-push 會逐個 W 查（`scripts/walkthrough_record_lint.py`；只查 `created` 在 `TICKET_RULES_SINCE` 當天或之後、這次推送有改到的票），沒交代就擋；
  合流前可以先跑 `make walkthrough-lint`（`ref="feature/TK-12 feature/TK-13"` 一次查好幾條分支），規則與推送時相同。
  四題任一為「是」的票，「沒走的是」只能用來回報阻塞，不能拿來出貨（見〈先問：這張票准不准跳〉）——機器分不出這兩種，靠這條。
  版面類的 W（位置、裁切、對齊）用真人眼看——HTTP 腳本、HTML 檢查看不到版面（見〈憑據型態〉）。
  由來：源專案一張票寫了「另外兩頁的同款元件一併檢查」，W1 只是為了過檢查補的一行，一頁都沒走就合進 `stage`，案主在那一頁發現問題才另開一張票。
- **不可以**：把跳過講成「已驗證」、拿測試全綠當走查的結論、或默默不提。
  沒做就是沒做——**說了案主可以自己補走一遍，不說他會以為有人看過了。**

案例（源專案）：一張改了八句成功提示文案的票，畫面載入正常、停在登入頁，
但**點擊完全沒送達**——輸入框不聚焦、按「登入」沒有任何回饋，與本票程式無關。
當場決定跳過，票上寫明「八句提示沒有任何一句是用眼睛看過的」。

**這份分級只管人工走查，不管自動化測試。** 自動化測試不分級，該跑的範圍照 `run-checks`；
模組之間互相呼叫，交叉回歸的風險由守門測試與 CI 兜底。
測試要省時間請往「跑一次要多久」修，不要往「少跑幾條」修。

## 被別條 session 佔住時：讓開，不是跳過（源專案 v4.28.0）

**「本機的 port、裝置被另一條 session 佔著」不是跳過走查的理由。** 兩邊都讓得開：

- **開發伺服器**：多半有參數能自己挑一個沒人用的 port（預設那個不是唯一）；後端也可以另起一份只給這次走查用的。
- **裝置／模擬環境／瀏覽器**：另開一個沒人在用的（另一台模擬裝置、另一個瀏覽器設定檔），不要搶別人正在用的那個。
- 查誰佔著要**掃行程**（看每個行程的工作目錄屬於哪棵工作樹），不要只查固定的 port——照規則換了 port 的人會被漏掉。
- **交付訊息要寫明這次用的 port 與裝置**，別人才知道要讓開哪一個。

> **為什麼這條要單獨寫死**：源專案有三張票在同一天跳過走查，理由都是「被另一條 session 佔著」——
> 而讓開的做法**當天稍早就已經寫在這份檔案上了**。規則在場不等於有人套用。
> 代價是真的：同一批票裡只有一張後來補走查，一走就抓到**兩個上百條測試全綠也沒抓到**的缺口。
> **跳過一次走查 ≈ 出一次貨帶著使用者看得到的缺陷。**

**走完要收尾盤點**（源專案 v4.28.0；本體在 `AGENTS.md`「收尾要盤點」）：走查常會起開發伺服器、背景行程、模擬裝置，
這些不在工作樹清單裡。宣告收尾時**列出查了哪幾項、各是誰的**，不准只講「沒有東西要收」；不是自己起的不要關，先問。

## 走查在哪裡走：三型環境（源專案 v4.33.0）

| 型態 | 誰做 | 定位 |
|---|---|---|
| **① 本機**（本機跑的畫面＋本機後端） | agent | 走查的主場。能直接改資料造情境——要驗的幾種情境（例：沒附檔／附了檔／已回報無法執行）**多半只有本機造得出來** |
| **② 本機跑的畫面連整合環境（`stage`）的後端** | agent | **合法的補走管道**。票已合流 `stage`、本機當時沒走到的部分，收單前補走 |
| **③ `stage` 上使用者實際安裝或打開的那一版** | **只有案主** | agent 不做，**除非案主特別指示** |

**② 不是違規，不要把它讀成違規。** 源專案收單時補走查用的正是這條，其中一次抓到兩個上百條測試全綠也沒抓到的缺口。
它跑的仍然是本機的畫面程式，只是後端換成 `stage`。

**走 ② 要配兩道護欄**：

- **不按不可逆的動作**（送出、刪除、對外通知）——那會真的寫進 `stage`。
  前例：源專案一次走查刻意沒按「送出申請」，因為那種申請送出即生效、使用者不能自己撤回。
- **收單警語照掛**：「走查是用本機畫面連 `stage` 後端做的，
  **使用者手上安裝的那一版不一定含這些改動**」。

**agent 在 `stage` 的責任只有三件**（實機那一型歸案主）：

1. 確認**部署成功**——看部署流程真的跑到「部署完成」並打開 `stage` 網址，不是只看 push 成功。
2. 確認**網頁畫面在瀏覽器可用**（給案主的是他要看的那一頁的網址，不是根網址）。
3. **需要另外打包、安裝的客戶端（App、桌面程式），打包狀態要主動回報**——源專案有一次打包失敗、從未送到測試管道，
   當下沒有人發現，於是「`stage` 上根本沒有可測的版本」變成事後才知道。

### 預設走哪一型：① 本機（源專案 v4.37.0）

- **① 是預設**——它是唯一能直接改資料造情境的一型，抓得到 ②③ 抓不到的東西。
- **② 只在這兩種情況用**：票已經合流 `stage`，而本機當時沒走到的部分要補走；
  或本機造不出那個情境（例如要用 `stage` 上的真實資料）。用了就照上面兩道護欄辦。
- **③ 只有案主**，除非案主特別指示。
- 本機起不來，照〈走不了就跳過〉那節處理，**並且要照〈跳過之後怎麼做〉的格式吵出來**。

## 核心原則：測過程，不是測零件

案主的一次操作是一條**時間線**：
`看到入口 → 按下去 → 等待 → 看到結果 → （狀態隨時間改變）→ 確認完成`。
單元測試往往只驗其中一格。走查的責任是把整條線走完，**每一步都看實際結果**。

歷史教訓對照（每一條都在源專案真的發生過）：

| 只驗了 | 漏掉的下一層 | 事故 |
|---|---|---|
| 檔案裡有那段字 | 頁面根本沒 render | 範本註解整段印在畫面上 |
| 按鈕有渲染出來 | 沒有真的按下去 | 元件庫的對話框吞掉動作，按了沒反應 |
| 按下去有導頁 | 沒走完那一頁看結果 | 指定密碼繞過服務層，旗標沒清 |
| 每個零件的狀態都對 | 沒走過時間線 | 輪詢只 append 不更新，「傳送中」永遠卡住 |
| 斷言通過 | 斷言**永遠**會通過 | 對空資料庫斷言「沒有壞資料」 |

## 走查清單

### A. 入口（找得到嗎）

- [ ] **不知道功能在哪的人找得到嗎？** 從案主平常停留的頁面出發，不靠網址、不靠記憶。
      藏在列表頁「動作」下拉選單的功能等於不存在。
- [ ] 手機也找得到嗎？觸控裝置沒有 hover——只靠滑鼠移入出現的入口，手機上永遠按不到。
- [ ] 反向：**不該看到的人真的看不到？直接打網址也進不去？**
      藏按鈕擋不住 POST。
      欄位也一樣：票的「欄位權限：」列了多出角色、或收回權限的欄位，就用看不到的角色登入，照 `AGENTS.md`〈沒權限的欄位，哪裡都不出現〉的出口清單逐個找欄名與值。

### B. 操作（按下去有反應嗎）

- [ ] **真的按下去**，不是看按鈕存在。按了要在畫面上看得到後果。
- [ ] 按下去到有回饋之間**有沒有空窗**？超過一秒的無回饋會被當成「沒按到」而重按。
- [ ] 重複按會怎樣？送出中有沒有鎖住？
- [ ] 失敗會怎樣？**要看得到失敗與原因**，不能畫面上與成功一模一樣（靜默消失、沒有傳送失敗標示）。
- [ ] **這次讓某個東西「不能按／不能選／不能送出」的話，要驗兩條、缺一不可**
      （源專案 v4.54.0）：
      ① **行為**：按下去真的什麼都沒發生；
      ② **外觀**：它跟「可以按的時候」**看起來不一樣**，而且**要用量的**——
      抓 `getComputedStyle()` 比對透明度／底色／文字色至少一項有變。
      **`disabled === true` 不算驗過**：那是屬性，使用者看的是畫面。
      `cursor: not-allowed` 也不算（要滑過去才看得到）。
      > 案例（源專案）：某個確認鈕在沒換人時正確地不可按，
      > 但它的 class 那一族沒有停用樣式，畫面上是滿版主色。
      > 只在主控台驗了 `disabled === true` 就交件，被退回：
      > 「雖然不能點，但顏色沒變，這樣很像壞掉，應該要反灰」。

### C. 時間線（等一下之後對嗎）

- [ ] 任何**會隨時間改變的狀態**（傳送中、處理中、載入中……），要走完整條線：
      觸發 → 中間態出現 → 完成 → **中間態消失**。最後一步最常漏。
- [ ] 畫面是輪詢／增量更新的話：**已經畫上去的東西之後還更新得到嗎？**
      append-only 的機制裝不下會變的狀態。
- [ ] 背景工作（排程、佇列、webhook）完成後，畫面多久反映？案主會等到嗎？

### D. 資料邊界（舊資料、別人的資料）

- [ ] **新欄位遇上舊資料**：既有資料在新功能下長什麼樣？
      （例：歷史資料沒有新欄位，全部顯示成「傳送中」——要回填。）
- [ ] 空狀態：沒有資料時畫面說什麼？
- [ ] 中文與特殊字元真的能用嗎？測試用的資料庫引擎與正式用的行為可能不同
      （源專案的標籤搜尋就這樣假綠過）——懷疑時兩個引擎都跑。

### E. 一致性（畫面各處說法一樣嗎）

- [ ] 同一件事在不同位置的顯示**一致嗎**？徽章紅了、數字也要算到
      （徽章與頁籤兩套定義各說各話）。
- [ ] 同一個判斷只能有一份實作——散在前後端兩邊遲早走鐘。

### F. 對照拍板（行為跟案主要的一樣嗎）

- [ ] 回頭讀票的「需求細節」，逐條對照實際行為——尤其是**否定句**
      （「不強制」「不顯示」「不重複」）。源專案的「不強制改密碼」實作成
      「不設旗標」而不是「清旗標」，行為與拍板相反。
- [ ] 驗收標準裡凡是寫「案主實機驗證」的項目，**明確列給案主**，不要混在「已完成」裡。

### G. 版面（動到排版才做｜源專案 v4.20.0）

**「有開瀏覽器」不等於「有看」。** 源專案一排日期篩選交出去時，搜尋框底部 185、
日期欄底部 210、按鈕高 62——**三種高度、兩條底線**，外加一個被擠成紅色三角形的提示
（看起來像那一格填錯）。走查當下確實開了瀏覽器也截了圖，但截的是 **800×450 縮圖**：
25px 的錯位在圖上只有 14px、文字約 5px，**那個尺寸下瑕疵不可能被看見**。
案主放大截一張過來，問題立刻現形。

- [ ] **截圖用真實寬度**：桌機畫面 ≥1440、手機用裝置原生尺寸。**縮圖只能當索引，不能當證據。**
- [ ] **對齊用量的，不用看的**：同一列的控制項跑一次 `getBoundingClientRect()`，
      斷言**高度一致**與**垂直中線一致**。差 1～2px 可接受，差 10px 以上一定看得出來。
- [ ] **改到共用版面時，挑最極端的兩頁一起走**（源專案 v4.54.0）：
      欄位最多的那一頁、欄位最少的那一頁。**不分走查級別**——縮小走查也要走這兩頁，
      因為「別頁會不會爆開」不是深度問題、是範圍問題，B～E 那幾關再仔細也看不到它。
      為什麼要這樣做見 `ui-design` 的 `references/01-layout.md`（§1 佈局與層次）。
- [ ] **量完還要看一眼。** 量測只回答「有沒有對齊」，回答不了「好不好看、像不像壞掉」。
      版面題的兩種證據**都要有**：量出來的數字，以及一張真實寬度的截圖。
- [ ] **回報要附數字**，不要只寫「看起來對齊了」。

```js
// 貼進瀏覽器主控台，把選擇器換成這一列的控制項
JSON.stringify(['#search', '#date-from', '#date-to']
  .map(sel => { const r = document.querySelector(sel)?.getBoundingClientRect();
    return r && {sel, h: Math.round(r.height), mid: Math.round(r.y + r.height / 2)}; }))
```

> 本節**只在動到版面時適用**（新增或調整一列控制項、表單、清單工具列）；
> 純文案或純後端變更不需要。

## 測試的品質門檻（走查發現問題後補測試時）

1. **測試要能證明自己會紅**：寫完後把程式碼弄壞一次，確認對應測試真的變紅，再還原。
   反向驗證沒紅的測試等於沒寫（每張票的實作紀錄都要寫結果）。
2. **警惕永真斷言**：對空資料庫斷言「沒有壞資料」永遠會過。要自己造出「壞的前提」，
   再驗證修法把它變好（源專案回填測試第一版的教訓）。
3. **斷言要具體**：「預期丟出任何例外」連打錯變數名稱都算過；
   比對中文標籤可能命中說明文字而非按鈕（改用按鈕的網址斷言才準）。
4. **時間線用測試固定下來**：模擬「操作 → 輪詢 → 背景完成 → 再輪詢」的完整序列。
   注意測試環境常把背景任務設成同步立即執行，會把中間態壓縮掉——必要時繞過端點、
   自己控制背景任務的時機。

## 憑據型態：「走查過」三個字必須說清楚是哪一種（源專案 v4.34.0）

**問題不是後兩種存在，是它們與第一種共用同一個詞。** 至少三種東西都自稱走查，
而票面上長得幾乎一樣——於是「走查過」變成一句**沒有固定含金量**的話，
而案主的驗收決定正是靠它。所以：**可以叫走查，但必須標型態。**

| 標示 | 實際做了什麼 | 抓得到 | **抓不到** |
|---|---|---|---|
| **走查（真人眼看）** | 在瀏覽器或裝置上**真的點下去**，看畫面 | 版面、順序、辨識度、按下去的後果、時間線 | — |
| **走查（HTTP 腳本）** | 打真實端點，對回來的 HTML／JSON 斷言 | 端點行為、狀態碼、頁面上有沒有那段字 | **版面、對齊、hover、鍵盤、按了有沒有反應** |
| **走查（HTML 檢查）** | 讓伺服器把頁面渲染出來（不開瀏覽器），檢查欄位／區塊 | 欄位在不在、區塊順序 | 同上，**而且完全沒有互動** |

**後兩種是登入閘門逼出來的合理替代，限不能請人代登入的介面**（agent 不把密碼打進登入欄位；能代登入的見下一段），
它們比什麼都不做好得多——**這條規則不是要打擊它們，是要讓它們誠實標示**。
**例外：第四題為「是」時，那幾條關鍵流程用 HTTP 腳本或 HTML 檢查不算數**（見〈第四題：關鍵使用流程〉）；同一張票其他部分仍照上面分開標示。

**登入閘門有解的介面，不適用這個替代**（源專案 v5.4.0）：能照〈卡在登入〉請人代登入的介面，
只要結論是「使用者看到什麼、按得到什麼」，**一律要真人眼看**；
HTTP 腳本只能補**後端細節**（例：沒權限的角色打 API 被拒、回應的欄位值），不能當畫面的走查憑據。
真的走不了，照〈先問：這張票准不准跳〉辦（四題全否才適用〈走不了就跳過〉），不要改用 HTTP 腳本交差。

**設計圖（示意圖）交圖前也用同一把尺**（源專案 v5.35.0）：交圖前自己用真的點擊走過每個互動，
頁面全新載入、之後不先執行任何自己的程式碼，走完看主控台沒有新錯誤——這才算「走查（真人眼看）」；
用程式設值或在頁面上跑測試碼只能當補充，它會改到被測的頁面。做法見 `ui-design` 的 `references/mockup.md` 第 9 條與第 13 條。

**規則**：

1. **票面與交付訊息都要寫出型態**，不可以只寫「走查過」。
2. **後兩種必須同時列出「因此沒有被人眼看過的項目」**——這一條是強制的，
   因為那正是後兩種看不到、而案主會以為看過了的部分。
3. 一張票用了不只一種，就分別寫（例：某頁走 HTML 檢查、另一頁走真人眼看）。

**對照範例**（三種標示互不相同）：

- `走查（真人眼看）`：在裝置上實點，抓到三個上千條測試全綠卻仍壞掉的畫面層錯。
- `走查（HTTP 腳本）`＋未經人眼：某個動作的導頁與狀態碼驗過，
  **按鈕在畫面上長什麼樣、按得動嗎沒驗到**。
- `走查（HTML 檢查）`＋未經人眼：區塊順序與位置驗過，
  **版面對齊與實際觀感沒驗到**（頁面要登入、當時找不到人代登入，agent 不代打密碼）。

## 回報格式

走查完，回報案主時分成幾欄，**不要混在一起**：

- **走查級別**：用了哪一級、依據上面四題的哪一題（一行就好；免走查與縮小走查一定要寫）。
- **關鍵流程**（第四題為「是」時必填）：列了哪幾條、每條走到哪、哪個畫面是實走的。
- **憑據型態**：真人眼看／HTTP 腳本／HTML 檢查（用上一節的寫法；一張票有多種就分別寫；能請人代登入的介面，畫面的結論只能是真人眼看，HTTP 腳本只列後端細節）。
- **我驗過的**：走了哪條路徑、每步看到什麼。
- **沒有被人眼看過的**（型態是 HTTP 腳本或 HTML 檢查時**必填**）：具體列出哪些畫面／互動只有程式層的憑據。
- **只有你實機才驗得到的**：列成清單（例：通訊軟體實機收訊、真手機觸控手感、
  第三方服務的簽章網址）。程式驗不到的就明說，不要讓綠燈暗示「全部都好了」。
