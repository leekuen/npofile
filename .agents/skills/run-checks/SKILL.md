# 改完一定要跑的檢查

任何改動完成後，**至少**跑對應的檢查，全綠才算完成。
本清單由 setup 初始化時填寫、之後由 framework 入口維護（技術棧變了要同步改這裡與 Makefile）。

## 票務與框架一致性（一律要跑）

```
make check          # 目前至少包含 ticket-lint；專案檢查指令設定後會一併跑
```

## 檢查輸出不要接管線（源專案 v4.90.0）

**看到檢查自己印出「通過」才算過；輸出不要接 `| tail`、`| head`、`| grep` 這類管線。**
管線的結束碼是**最後一段**的（`tail`／`grep` 幾乎永遠成功），檢查失敗時整行仍然回報成功，
畫面上又只剩最後幾行，看起來像過了。源專案一個月內兩次因此把格式錯誤推上去、到 CI 才紅；
「看到通過才算過」這條文字規則早就有，仍然再犯，所以改用機器擋。

- 擋的是 PreToolUse 閘門 `scripts/check-pipe-gate-hook.sh`；哪些指令算「檢查指令」由
  `scripts/framework-config.sh` 的 `NO_PIPE_COMMANDS` 決定（一筆寫指令開頭的幾個詞）。
  上面〈專案檢查指令〉新增一條，就把它補進 `NO_PIPE_COMMANDS`，閘門才擋得到。
- **要留完整輸出、或只想看尾段，就導到檔案再讀**（`make check > out.txt 2>&1; echo "exit=$?"`），結束碼才是檢查自己的。
- 閘門只看指令字串，存成變數、包進 `eval` 之類的寫法認不出來——擋不到的那些，靠這條規則本身。

## 跳過的測試要講出來（源專案 v4.85.0、v5.39.0）

**`OK (skipped=N)` 不等於全過**：回報時要講**跳過幾條、為什麼**。

- 源專案本機少了某個執行環境，約 52 條測試被安靜跳過、結果照樣打勾，推上去 CI 才紅兩關。
  所以**測試缺必要的執行環境時，寧可明確失敗並印出要怎麼補，不要安靜跳過**；跑完印出共跳過幾條，
  比平常多就是警示。
- CI 也一樣：**最新一次 CI 裡該跑的那一關顯示「skipped」不算綠**——它沒有跑，什麼都沒證明。合流前要看的是真的跑完、真的綠。

## 什麼時候跑多少：三層（源專案 v5.20.0）

本機不必每次跑全套（全套交給 CI）；**跑多少照時機分三層**：

1. **開發中**：只跑這次改到的相關模組。
2. **交合流前**：一律跑一組**快速的守門測試**（清點／一致性型：某份清單的數量、欄序、
   唯一出處、前後端兩份目錄一致這類——單一分支最常不小心弄壞的舊測試），不管這次改了哪裡；
   守門組由專案在〈專案檢查指令〉定義。新寫這一型的測試，就把它加進守門組。
3. **合流後、推 `stage` 前，由做合流的那條 session 在合流好的程式上跑**「這次合進來的票改到的模組」整組＋守門組
   ——**不拿當初開發 session 的綠燈當數**：兩條分支各自綠，合起來不一定綠。
   - 好幾張票一起合：在一棵整合用的工作樹合好，所有票改到的模組取聯集，**只跑一次**，不要每張各跑一遍。
   - 單張票：可以在那張票的工作樹先 `git merge origin/stage`（程式就等於合流後的樣子），在那裡跑。
   - CI 紅了修好重推前，只跑修正動到的模組＋守門組，不再跑一輪整組。

> 為什麼這樣分：源專案一個月內整合分支的測試紅燈，約一半是單一分支自己弄壞了已經存在的舊測試——
> 本機擋得到，其中多數被守門組擋、少數要合流後的整組才擋得到；而本機跑全套要半小時、又跟 CI 重複。

## 假綠比假紅嚴重（源專案 v4.32.0）

**假紅很吵、會逼人去查；假綠是跑完看到全綠就合上去。** 所以兩者不是同一個等級的問題：
測試指令**測到的不是你這棵工作樹的程式碼**（環境掛到別的目錄、打到別人的伺服器）卻顯示全綠，比測試壞掉更危險。

- **新的測試指令、或懷疑某條指令測的不是自己的程式碼時，用「植入必紅」驗收**：故意把被測的程式改壞一處，
  跑一次——應該紅的沒有紅，那條指令就是假綠；確認紅了再改回去、再跑一次綠。
- 能擋就讓它變成不可能，不要靠人記得：例如指令開跑前先比對「它要測的目錄」跟目前所在的工作樹是不是同一棵，不一致就中止並印出兩邊路徑。

## 多介面同步

若變更是使用者可見功能、API 契約、權限、狀態流程，且專案有多個介面（Web / Mobile / 桌面），
除非使用者明確限定只改單一介面，必須同時檢查並驗證所有介面已同步。

## 回報

- 把實際指令輸出講清楚；測試有失敗就貼出失敗內容，不要宣稱通過。
- 有跳過的測試，講跳過幾條、為什麼（見上面〈跳過的測試要講出來〉）。
- 檢查不是綠燈就不算完成。
- 若只改單一介面，要說明是使用者明確限定，或其他介面無需同步的具體原因。

## ⚠️ 綠燈不是終點：下一關是走查（源專案 v4.33.0）

**這份清單驗的是零件，案主用的是過程。** 改到**使用者看得到／按得到**的東西
（畫面、按鈕、表單、訊息、狀態顯示、流程順序）時，綠燈之後**必須接 `user-walkthrough`**
——按鈕按了沒反應、狀態永遠卡在「傳送中」、功能存在但入口找不到，這些本清單全綠也擋不住
（源專案有一次上千條測試全綠，某一類資料的詳情頁卻每一筆都打不開）。

- **預設檔位是「縮小走查」**，不是全清單（源專案 v4.26.0）。
- 純後端重構、純文件、純 CI 可以不走，但**要在回報裡寫明為什麼跳過**；例外見 `user-walkthrough` 第四題。
- 判準與清單以 `user-walkthrough` skill 為準，不要在這裡另記一套。
