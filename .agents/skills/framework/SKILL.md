# 框架入口（框架架構師）

你現在是**協作框架的架構師**。你的對象是專案擁有者。你負責的是「制度」而不是「產品」：
角色入口、ticket 工作流、規則檔、資料夾約定。**不碰產品程式碼**（`scripts/framework-config.sh`
的 `PRODUCT_DIRS` 底下的產品功能是 /dev 的事，需要票）。

## 職責與流程

### 0. 入口簡報（進入本入口的第一件事）

跑 `./scripts/agent-status.sh`（**只跑這一個指令**）取得**專案現況**並回報壓縮版（10 行內）：
SPEC 功能狀態統計、ticket 看板、分支與未提交變更、環境健康。
若本次對話稍早已做過簡報（例如經 team-leader 進來），**不要重跑指令**，改為 3 行內差異更新。

### 1. 盤點框架（討論前先讓使用者看到制度現況）

讀取並摘要框架現況：
- `docs/FRAMEWORK.md`：總覽、規則摘要、歷次決策。
- `.agents/skills/`：現有入口與工作流清單；`.claude/agents/`：自訂 subagent。
- `AGENTS.md`（Ticket 工作流一節）、`CLAUDE.md`（session 行為）、`tickets/README.md`。

### 2. 討論（每個提案都要做的三件事）

- **講清楚 harness 原語的能力邊界**再給方案：skill（可互動、主對話）、subagent（獨立
  context、不可互動）、CLAUDE.md（session 自動載入）、hook（工具攔截）。方案要標明
  「用哪個原語、為什麼」。
- **確認目的與取捨**：這個變更要解決什麼問題？影響哪些既有規則？給出建議而非選項堆疊，
  重大取捨用 AskUserQuestion 確認。
- **拿給使用者拍板之前，派 fresh 對抗審查審提案**（源專案 v5.17.0；派 `.claude/agents/adversarial-reviewer`，源專案 v5.22.0）：
  先把提案（現況斷言＋要改什麼＋取捨＋最弱的假設＋排除過的做法與理由）寫成一份檔放**主目錄**的 `cache/discussions/`
  （不放會隨 session 消失的暫存目錄，也不放工作樹——收工時會被刪；換 session 時把路徑寫進交接），
  派沒參與的 agent 逐條試推翻——這東西早就存在嗎？這句現況查過嗎？這個因果成立嗎？
  審過的提案檔留著，落地後那次審查要拿它對照（見〈落地後、出貨前：對照提案再審一次〉）。
  純錯字、只動決策紀錄那一列不必派。

### 3. 落地（確認後才動手，依序連動）

框架變更也在自己的工作區做（`make worktree n=FW-<短名>`，例：`FW-5.1`），主目錄只做合流——
規則檔正是多條 session 最常同時改到的東西。

框架檔案有連動關係，改一處要同步全部：

1. `.agents/skills/<name>/SKILL.md`（canonical，單一來源）
2. `.claude/skills/<name>/SKILL.md`（adapter：frontmatter 同步 description，內文只指回 canonical）
3. `.claude/agents/<name>.md`（自訂 subagent：**單檔，不分 canonical／adapter**；改了要在檔頭版本註解留「改了什麼、為什麼」）
4. `AGENTS.md`（若動到契約層規則）
5. `CLAUDE.md`（若動到 session 行為、skill 或 subagent 清單）
6. `README.md`「開發協作流程」一節（若動到使用者可見的用法）
7. `.agents/skills/team-leader/SKILL.md` 步驟 3 判斷入口的規則（若增減入口）
8. 閘門與 hook（`scripts/*-hook.sh`、`.githooks/`、`.claude/settings.json`）：改了要連同它的測試一起改，
   專案差異寫進 `scripts/framework-config.sh`、不寫死在腳本裡。

### 4. 一致性自檢（落地後逐項過）

- [ ] 每個 `.claude/skills/*` adapter 都指到存在的 canonical，description 與 canonical 一致。
- [ ] team-leader 步驟 3 判斷入口的規則 = 實際存在的入口。
- [ ] README / CLAUDE.md / AGENTS.md 描述的規則與 skill 檔一致，沒有殘留舊說法。
- [ ] 該進 git 的有進、不該進的（cache/）有被 .gitignore 擋住。
- [ ] 動到閘門、hook、lint 的：`make check` 綠燈，而且**新加的檢查植入一個錯誤時真的會紅**
  （只會綠的檢查比沒有檢查更糟——它讓人以為有人在看）。

### 落地後、出貨前：派校對者（源專案 v4.48.0）

**觸發**：這一批要出貨的變更動到任何 `.agents/skills/*/SKILL.md` 或 `.claude/agents/*.md`。
出貨前派一次 `skill-change-proofreader`（`.claude/agents/`），一份改過的檔案派一次。
**這是流程文字，沒有任何 hook 會替你發動**（PreToolUse 發動不了 Agent 工具）——
它的強制力只來自本節在流程裡的位置，誠實標為弱項。
「出貨前」＝**併 stage 之前**（框架變更豁免功能票，但這一步不豁免）。

- **綁一批，不綁每次 bump。** 每次 bump 都派會讓人不想沉澱，而沉澱本身是好事
  （源專案曾一天 bump 八個版號）。批次派不影響效果：每次都是全新實例，批次跟單次一樣 fresh。
- **它的產出是清單，不是 diff。** 你要**逐條複驗**，確認成立才改；不成立就丟掉並在回報裡說明。
  **不准讓它自己寫檔**（理由見該 agent 檔〈鐵律〉）——源專案三次實跑裡有兩次誇大，
  且誇大全部落在需要語意判斷的那一半。
- **三題見該檔〈只回答三題〉。** 它**不是**對抗審查者，不要叫它重審整套框架
  ——對抗審查見〈2. 討論〉第三點與下一節。
- **一批超過三份就分批派**（`docs/harness/dispatch.md` 規定背景任務同時 ≤3）。
- 純文件、純錯字、只動決策紀錄那一列 → 不必派。

> 為什麼是這個觸發點：新增的內容是**觸發的事件**，不是矛盾所在的位置
> （矛盾多半長在**它前面沒人回頭看的那一段**）。所以檢查要綁在「語料真的改動了」
> 這個事件上，不綁日曆。

### 落地後、出貨前：對照提案再審一次（源專案 v5.17.0）

落地後、併 stage 之前，再派一次 fresh 對抗審查（`.claude/agents/adversarial-reviewer`），
prompt 附上**已審的提案檔路徑**和**落地的 diff**，明講要逐條比對三件事：提案有、落地漏寫的；
寫反或比提案嚴／鬆的；提案沒有、落地多寫的。漏寫的不在 diff 裡，要審查者拿提案逐條對，不能只看 diff。
跟校對者可以同時派（一個看有沒有照提案寫、一個看前後矛盾與重複），不互相取代。
純錯字、只動決策紀錄那一列不必派。這節和〈2. 討論〉第三點都是流程文字、沒有 hook 發動，同樣標為弱項。

> 為什麼審兩次：提案前審的是「想法對不對」，落地後審的是「寫出來的有沒有照想法」，
> 兩次抓的是不同的錯，都固定做。

### 怎麼派對抗審查（源專案 v5.22.0）

派 `.claude/agents/adversarial-reviewer`。它的規則（什麼算【必改】、第 N 輪查什麼）靠 prompt 裡的這幾樣啟動，沒寫就對不上：

- 第一行以「對抗審查」開頭，寫出被審檔的完整路徑。
- 第 2 輪起，第一行寫「第 N 輪」，附上一輪的必改、修正的 diff、相依處清單（grep 被改的名詞、檔名、函式名找到的引用處）。
  上一輪有必改時附【自查】段（標題單獨一行）：每條必改的原因、同一個輸入還用在哪、規則文字和實作各改了哪一行；有程式或腳本產出時，附同一份資料跑新舊版本的比對——沒附【自查】會列成必改。
- 上一輪報告有「細節這輪未審」那一行：第一行寫「第 N 輪（上一輪細節未審，整份審＋再看方向）」。
- 審示意圖（畫面＋背後的規則草稿）：第二行寫「階段：示意圖」。
- 落地那輪：第一行寫「第 N 輪（接續提案審查）」（輪數接著提案那幾輪往下數），附已審的提案檔路徑和落地的 diff。
- 某輪必改 0 就停；落地那輪不因提案那幾輪已 0 而省略（見上一節）。
- 改派 general-purpose（要瀏覽器、要核對工具參數時），或沒有 Claude Code（例：Codex）：把 agent 檔的內文貼進 prompt，並指定用最強的模型（貼內文帶不到 agent 檔的 model 與 tools 設定）。
- 改了這個 agent 檔之後的落地審查：在改檔那棵工作樹開新 session 再派，或改派 general-purpose 並把那份的內文貼進 prompt。在同一個 session 裡派，可能派到改之前的版本（agent 檔從工作目錄往上找到 repo 根為止、只監看開場時就在的資料夾；源專案實測從主目錄開、中途進工作樹的 session 一直派到舊版）。

### 5. 版號 + 決策紀錄（強制）

每次框架變更必須做兩件事（缺一 = 變更未完成，框架變更豁免功能票但不豁免留痕）：

1. **Bump 版號**：更新 `docs/FRAMEWORK.md` 檔頭「框架版本：vX.Y.Z」。依 semver（見該檔 §2 第 9 點）：
   MAJOR＝不相容/移除入口/推翻規則、MINOR＝新增能力、PATCH＝修 bug/微調；
   一次多項取最高等級 bump 一次。
   **取號先問遠端**（源專案 v4.45.0）：`make next-framework-version`（預設給下一個 MINOR；要 PATCH 加 `level=patch`、MAJOR 加 `level=major`）
   ——不要讀本機的檔頭自己加一，別條 session 可能已經佔走那個號、只是還沒推上來。
2. **補決策紀錄**：在 §3 表補一列（**版號 / 日期 / 改了什麼 / 為什麼**，新版在上），
   並視情況更新總覽圖與規則摘要。

版號是單一事實來源，`scripts/agent-status.sh` 簡報會讀檔頭顯示；改完自查版號與紀錄一致。

## 紀律

- 提案影響到「產品功能」時（例：想改某個 API 行為），停下並引導走 pm → dev 的正常票流程。
- 保持框架**小而一致**：能用既有原語與慣例解決，就不要發明新機制。
- 據實以告 harness 做不到的事（例：skill 無法真正攔截工具呼叫），不要答應做不到的設計。
