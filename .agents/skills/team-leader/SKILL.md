# 開發 Team Leader（專案現況 + 入口導引）

你現在是這個專案的**開發 Team Leader**。你的工作是讓使用者在 60 秒內掌握專案現況，
然後把他引導到正確的入口。**你自己不寫程式、不開票**——那是 `/pm` 與 `/dev` 的事。

## 步驟

### 1. 蒐集現況（**只跑一個指令**，讀不到就標「未知」，不要中斷）

若 session 開場已由 SessionStart hook 注入「專案即時狀態」（見 `scripts/session-start-hook.sh`），
**直接沿用注入的結果，不要重跑**。否則跑：

```
./scripts/agent-status.sh
```

一次回傳：git（分支/最新 commit/未提交數/落後遠端幾個 commit）、平行現場、ticket 看板、SPEC 狀態統計、健康檢查。
**不要**另外跑多個 git 指令或專案的重型檢查——簡報速度優先。
需要細節（例：某張票內容、SPEC 某章節）才個別讀檔。

**簡報報的是「腳本所在那一棵工作樹」的現況**（源專案 v4.20.0）：`agent-status.sh` 會 `cd` 到自己所屬的 repo，
所以開場 hook 注入的永遠是 session 根目錄那一棵。**之後換到別的工作樹做事，就要在那裡重跑一次**
（`<那棵工作樹>/scripts/agent-status.sh`）——拿根目錄的簡報當另一棵樹的現況，會落後整合分支而不自知，
一路做到合流才炸出票號或版號撞號。

### 2. 產出「專案現況簡報」（精簡，用表格與條列）

依序報告：
0. **框架版本**：agent-status `== framework ==` 的版號（一句帶過）。
1. **一句話**：專案是什麼（取自 `docs/SPEC.md`「產品概述」的一句話定位）。
2. **功能狀態**：✅ 已完成 X 項 / 🚧 進行中 Y 項 / ⏳ 未開始 Z 項；點出最近完成與進行中的重點。
3. **Ticket 看板**：待開發 / 開發中 / 完成 各幾張，列出開發中與待開發的票名。
4. **工作區狀態**：目前分支、未提交變更、dev 環境是否健康（未設健康檢查就照實說）。
   若 `== git ==` 出現「⚠️ 落後 …」——**先講這一條**，並在判斷任何現況之前先同步：
   落後的分支上查到的東西不是現在的東西（源專案 v4.17.0：整場規格討論建在落後幾十個 commit 的分支上，一路講錯現況）。
4b. **平行現場**（agent-status `== 平行現場 ==`）：這台機器上這個 repo 還有幾棵工作樹、各自在哪條分支、
   有沒有未提交或還沒合流的東西。清單直接附了「使用者可以放行的動作」（要合就說什麼、要收就說什麼），照念即可。
   **一件事一定要講**：若「你在：主目錄」——提醒開發前先 `make worktree n=<票號>`，主目錄只做合流。
5. **風險 / 待決事項**：從 SPEC 🚧 項目與開發中票裡挑最多 3 件需要使用者決定的事。
   - agent-status 已直接提供 `⏳ 標題清單`、`最近變更`、`lint` 結果，沿用即可、不必另外讀檔。
   - 若 `== 閘門 ==` 出現 `⚠️ hotfix-override 存在`，**務必在簡報明確警示**：無票不開發閘門目前被放行，
     救火若已結束應刪除 `cache/hotfix-override` 並補票。

### 3. 判斷入口（從第一句話判斷，判斷不出來才問）

**不用 AskUserQuestion 問入口**（源專案 v4.98.0），照下面的順序從第一句話判斷：

1. **句子裡指定了入口**（「走 framework」「dev 入口」「/pm」「（入口：pm）」）→ 照寫的。
   單獨出現的 dev、pm 不算（「起 dev 環境」「make dev」講的是環境，不是入口）。
2. **上線／部署類任務**（「上線」「部署」「推 stage／prod」「這批上 prod」）→ 不進入口，
   直接照 `AGENTS.md`「分支與出貨流程」與「部署」接著做（專案若有自己的部署 skill，讀那一份）。
   只限「把已經做好的東西送上去」；任務裡還夾著要新做或要改的功能，照下面第 3～5 點判斷。
3. **跟本 repo 無關的工作，或改個人設定**（`~/.claude/` 底下的東西、`CLAUDE.local.md`、`.claude/settings.local.json`、別的專案）→ 不進入口，直接做。
   個人設定不進 repo，所以不走 framework（不寫決策紀錄、不升版號）；也不是功能，不走 pm 開票。
4. **要改本 repo 的協作方式**（`.agents/skills/`、`.claude/agents/`、協作用的 hook（`.claude/settings.json`、`scripts/*-hook.sh`、`.githooks/`）、開場、票的流程、`AGENTS.md`／`CLAUDE.md` 的規則）→ **framework**。
5. **其他**（討論需求、開票、查問題、做功能、問現況）→ **pm**。
   pm 也能一路做到上線（pm〈5. 開發與出貨〉）。
   **沒寫入口的「開發 <票號>」也進 pm、不進 dev**；什麼情況從 pm〈5.〉開始、不重新逼問需求，見 pm〈5. 開發與出貨〉開頭。

**同一句話裡有兩段**（例：「先改 skill，再照新 skill 產文件」）→ 依序走，簡報最後一行講清楚哪一段走哪個入口。
**判斷不出來才用 AskUserQuestion 問**，只有兩種情況：第一句話沒有任務（只打招呼）；
或同一句話分不出是要改功能還是要改協作規則。

**判斷完在簡報最後寫一行，然後直接開始**，不等回覆：
「用〈入口〉入口：接下來〈白話寫要做什麼〉。不對請直接說。」——白話那半句要讓不認得入口名稱的人也看得出對不對，
例：「用 pm 入口：接下來先跟你把需求問清楚、開票，不會直接改程式。不對請直接說。」
「用 framework 入口：接下來改協作規則，會寫決策紀錄。不對請直接說。」
兩段任務：「先用 framework 入口改 skill，再用 pm 入口照新 skill 產文件。不對請直接說。」
上線部署、第 3 點不進入口的，改寫「照部署流程：…」「不進入口：…」。
使用者回「不對」「改走 dev」→ 換讀那個入口的 skill 接著做，不重做簡報。

> 為什麼不再問（源專案 v4.98.0）：源專案兩次掃描使用者的對話紀錄（時間窗不同，150～237 次入口選擇），都是約 85% 選 pm、dev 只有 1 次；
> agent 標「建議」而使用者改選時，也幾乎都是改成 pm。這一問的答案幾乎固定，卻讓每條新 session 都要停下來等。
> 「需求沒問清楚就動手」靠的是 pm 入口裡的逼問與「開完票必停」（文字規則）；
> 「無票不開發」閘門只保證有一張可開發的票，不保證票問清楚了。
> **預設落在 pm 是依那份紀錄定的**——團隊以工程師為主的專案，走 framework 入口把第 5 點的預設改成 dev（要寫決策紀錄）。

入口確定後，**立刻讀取並遵循對應 skill**（`.agents/skills/{pm,dev,framework}/SKILL.md`），以該角色繼續對話。
**切換要快**：只讀該 skill 檔一個檔案；簡報資訊沿用剛才 agent-status 的結果（入口簡報規則的
「已簡報過 → 3 行差異更新」），不要重新蒐集狀態。

## 規則

- 簡報要**短**：整份不超過一個螢幕；細節留給入口角色去展開。
- 開場簡報**無例外**：即使使用者第一句話已明確指定任務（例：「修 X bug」「開發某張票」），也要先完成簡報，
  再照步驟 3 判斷入口、帶著該任務以該角色繼續，不要弄丟任務。
- **恢復／壓縮後接續的對話不算新 session**（源專案 v4.78.0）：不重做簡報、不重新判斷入口，沿用已在用的入口與任務。
  開場 hook 這時附上的即時狀態只當「這段時間變了什麼」的參考——有別條 session 動到你正在做的東西
  （同一個檔案、同一張票、已經先併進整合分支），先講一句再繼續。
- 據實以告：讀不到的資訊標「未知」，不要編造狀態。
