# dispatch.md — 調度與判準（主檔，上限 60 行）

> 來歷標記：[C1]~[C9]=真實案例（見檔尾）；[猜]=無案例佐證，2026-10-01 到期仍未驗證即提議刪除。
> 完整論述在 archive/（翻舊帳用）；模板在 templates/；維護規則在 maintenance.md。

## 下場門檻 [C4]
主對話可自己做：讀 ≤2 個已知檔且合計 ≤300 行、單次 grep、編輯 ≤3 個已讀檔、跑單一驗證指令。
超過 → 派工。判準：產出的「原文」不需要留在主對話，就派。留在主對話的每一行，之後每回合重複計費。

## 派工表（成本檔位：平衡）[C4]
| 情境 | subagent_type | model |
|------|---------------|-------|
| 定位/掃描 | Explore | haiku（純定位）/ sonnet（需語意） |
| 方案規劃 | Plan | opus |
| 有票實作 | general-purpose + isolation:"worktree" | sonnet |
| 機械批次 | general-purpose | haiku |
| 難 bug / 資安 / 跨模組 | general-purpose | opus |
| 驗收（fresh context） | general-purpose | sonnet；高風險 opus |

Agent 工具無 effort 參數；fable 平常不可用；猶豫就選 sonnet。背景任務同時 ≤3 個，完成自動通知、不輪詢。

## 派工三件套（缺一不派）[C4]
目標與動機／驗收條件（可打 ✅❌ 的句子）／回報格式（≤15 行；長產物落檔傳路徑，不貼 >30 行原文）。
**審查型 agent（`.claude/agents/` 那幾支）不受 ≤15 行限制**，以「每條發現兩行」為預算、砍條目不砍證據（行號與原文片段一律留）——`breaker` 要列至少 40 條、校對者固定五段輸出，15 行裝不下（源專案 v4.48.0）。
subagent 看不到本對話：prompt 自包含，禁「如前所述」。直接用 templates/ 填空；實作的共通規則在 templates/implement.md〈共通規則〉，prompt 只引用不重貼（源專案 v4.81.0）。

## 升降級（防重試螺旋）[猜]
haiku 敗 1 輪→升 sonnet；sonnet 敗 2 輪→帶完整失敗軌跡（原任務+輸出+驗收差距）升 opus；
opus 敗 2 輪→停，給使用者三選項（換方法/放寬驗收/人工介入）。**無第三輪**。
opus 解出模式→寫成「模式+範例」批次派 haiku/sonnet 套用。微調 prompt 重派＝計入輪數。

## 驗證不自驗 [C1][C4][C8]
寫的人不驗收；驗收派 fresh-context（templates/review.md）。文件＝read-back；程式碼＝實跑測試；
對外動作＝驗終態：push 後查 `gh run` 結論、部署後打 healthz、寫檔後讀回 [C1]。
高風險（資安/金流/權限/刪資料）＝第二意見（兩個獨立 agent），結論衝突升使用者 [猜]。
**批次時誰需要獨立驗收**：碰權限／金額／隱私／狀態判斷的票才派；純文字、小 UI、單一畫面的票由開發者自驗＋整合時跑一次整套測試 [C8]。

## 完成的定義（五條全過才說「完成」）[C1]
逐條驗收有證據／fresh 驗收通過／make check 對應子集綠燈／票+SPEC+FRAMEWORK 留痕同步／
無隱瞞（失敗的測試、跳過的步驟、殘留問題明列）。

## 一次收到多條指令：做完全部再整檢一次（源專案 v4.59.0）
每一條做完只驗自己那一條，**全部做完再整檢一次**（跑該功能的完整回歸清單、真實畫面走一遍）。逐條做、逐條回報會連鎖回歸——第 N 條修好第 N-1 條弄壞的、第 N+1 條又弄壞第 N 條；源專案一次八條指令裡三次回歸都是這個形狀：新加的那條路走了，被它影響的舊路沒走。

## 停下問使用者 [C2]
不可逆或對外（push/merge/部署/刪資料/secrets）——本次已授權的具體動作除外，授權不外溢；
規格兩種合理解讀且產出不同；閘門或權限擋下（不繞過）；diff 規模遠超任務描述。
品味題（文案語氣/UX 取捨）：找專案先例→出 2-3 案附取捨讓使用者選，不硬拍板 [猜]。
不問：有專案慣例可循的內部細節（命名、測試位置——照 AGENTS.md 與周邊程式碼辦）。

## 換路訊號（換路，不是重試）[C2][猜]
蹺蹺板（修 A 壞 B）；同段邏輯出現第 3 個特判；同一錯誤「修好」後再現；為過驗收而改驗收（立停）。
換路前寫一行「原路線為何不通」，防下一輪走回頭路。

## 先查證再斷言 [C3][C5][C6]
「看不到」≠「不見了」。下結論前用第二種方法交叉查：`git branch --contains`、`gh run`、實跑。
提案／檢討的每條現況斷言（「X 不存在」「Y 只查本地」）要本 session 實跑查過並註明查法；查不了的標「未查證，推測」。掃兩支檔就斷言「沒被蓋到」＝超出證據 [C5]。
重大提案（框架變更、多條建議的檢討）送出前自派 fresh 對抗審查（`.claude/agents/adversarial-reviewer`；prompt 寫法見 framework SKILL〈怎麼派對抗審查〉）：逐條試推翻（已經存在嗎？這句查過嗎？），不是「看看有沒有問題」[C5]。落地後、併 stage 前再派一次，對照已審的提案核對落地文字（源專案 v5.17.0，見 framework SKILL〈落地後、出貨前：對照提案再審一次〉）。
**「系統現在會不會 X」以實際畫面為準，不能只讀後端程式碼推論** [C6]：讀後端只證明有沒有那條邏輯，證明不了畫面上有沒有那個東西。查法是把那一頁跑起來看；查不了就標「未查證，推測」，不用肯定句。
subagent 的回報也是斷言：主對話引用或合回前自己再查（實作看 diff 與測試輸出；審查型產出逐條複驗，見 framework SKILL〈落地後、出貨前：派校對者〉、AGENTS.md「背景 subagent（長任務）」）。

## 往迴圈裡加查詢就要量 [C7]
判準：這一行會不會**對整個池子跑一輪**（全部使用者、全部單據）？是的話，加進去之前就量（查詢次數＋耗時，十行就寫得出來）——**測試全綠、畫面也看不出來**，只有等的人知道。「本來就已經是 N+1，我只是多加一次」不是理由，慢就是這樣累積出來的。

## 背景任務：先看到輸出才說「在跑」 [C9]
丟到背景（測試、部署盯梢、長指令）後，**先看到第一行輸出才回報「已在跑」**；對話壓縮或接續後，先確認執行環境（容器、dev server）還活著，再說「已重跑」。沒看到輸出就說在跑，是把「我下了指令」講成「它在跑」（源專案 v5.25.0）。

## 案例（來歷；出自源專案，決策細節見 archive/FRAMEWORK-history.md）
> 出處寫 repo 內查得到的地方（決策紀錄、票），不寫 repo 外的記憶檔名——別人讀不到、檔名也會消失（源專案 v4.86.1）。
- C1：push 成功但 CD 一直失敗（SSH secrets 未設；`gh run` 可證）→ 驗終態、DoD。
- C2：早期假設使用者角色致登入權限反覆重構（history v1.0.0 決策列）→ 問人、換路。
- C3：`git log -5` 沒看到 commit 誤判被強推 → 先查證。
- C4：A/B 探針＋源專案一張票實測：制度組派工+獨立驗收，主對話僅 +2k tokens（舊模式 ~25k）→ 門檻、派工、三件套。
- C5：提案「新做一支環境盤點腳本」重造了早已存在的狀態腳本，被使用者追問「你確定嗎」才查出（源專案 v4.21.0）→ 斷言附查證、對抗審查。
- C6：斷言「改完要存檔才看得到結果」，使用者直接貼出畫面上早就即時顯示的那一行；當時只讀了存檔後的訊息邏輯、沒跑那一頁。同族第三次（前兩次：信了程式碼註解的自述；只比對字串有沒有出現、沒看使用者實際看到什麼），所以升成硬規則（源專案 v4.86.1 改寫）→ 現況以畫面為準。
- C7：往一支對每位使用者各跑一次的函式裡多加一次查詢，上線後「載入要好幾秒」，實測 1,950 次查詢／2.7 秒；改成一次撈完是 8 次／165 ms，花的時間遠少於當初量一次（源專案 v4.45.0）→ 加進迴圈前先量。
- C8：一批十六張票每條線派一位獨立驗收、共八位，四位（約 60 萬 token）沒抓到擋出貨的問題；抓到真問題的是隱私（地址只差一字就把完整地址給了不該看的人）、狀態判斷（改了日期後狀態標籤沒回到原本該有的狀態）與整合時的整套測試（源專案 v4.81.0）→ 驗收只派高風險票。
- C9：對話壓縮後執行環境已停，指令立刻失敗卻回報「已重跑」（源專案 v5.25.0）→ 先看到輸出才回報。
