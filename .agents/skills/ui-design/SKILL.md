# UI 設計檢查（通用 · 及格門檻）

這是一份**通用、可跨專案**的 UI/UX 基本準則。目標是「**及格**」——讓第一版設計就沒有明顯毛病，
不是追求完美，也不要在 UI 上耗過多時間。國際通用慣例的濃縮（Nielsen 十大可用性原則、
Apple HIG／Material 的常識、Refactoring UI 的實務）。

**邊界（本 skill 不管的）：**
- **文案／用字** → 用 `ux-writing` skill（怎麼「說」）。
- **某專案專屬的具體選擇**（人工定的色票 hex、特定共用元件名、術語）→ 在該專案的「設計語言」
  （專案自己記在 `AGENTS.md` 或設計文件裡的那一套，加上 `ux-writing`〈術語表〉）。本 skill 只說「**要有**一套語意色、
  別各畫面亂配」；具體「是哪幾個色」看專案設計語言。

## 何時用

- **開任何新畫面/元件、或改動既有 UI 前**：先過〈開工前檢查〉。
- **做完後**：當自我 review 清單再過一次，抓明顯問題。
- 平台不同、原則相同：App 與後台都適用，差別只在元件與尺寸。

> **機制化**（源專案 v4.6.0 起）：寫入「畫面層檔案」（哪些路徑算，看 `scripts/framework-config.sh` 的 `UI_PATH_GLOBS`；留空＝不擋）
> 前，PreToolUse `scripts/ui-design-gate-hook.sh` 會擋，直到本 session 啟動過本 skill（啟動時 `scripts/ui-design-mark-hook.sh` 會印 🎨 banner 留痕）。
> 確非設計工作（如只改字串 typo）時，經使用者同意 `touch cache/ui-design-override` 放行、事後刪。
> **示意圖**固定放 `cache/demos/`（`cache/` 不進版控）；圖上的每一句字先照 `07-restraint.md`「這句話在做什麼工作」那張表分類、
> 再照 `ux-writing` 寫——第一次寫 `cache/demos/` 的示意圖時 `scripts/mockup-text-gate-hook.sh` 會先擋一次、把那張表推到眼前。

## 開工前檢查（一頁快篩）

- [ ] **一個畫面一個主目的**，標題講清楚這頁在幹嘛；相關資訊群組在一起、別太擠。
- [ ] **主要動作明顯、好找、好按**：不要逼使用者捲到底才找到；一頁以一個主要按鈕為主，次要動作弱化。
- [ ] **四種狀態都想過**：正常、**載入中**、**空**、**錯誤**——每種都有對應畫面，不要只做「有資料且成功」那種。
- [ ] **每個操作都有回饋**：成功/失敗/處理中要讓人知道；送出中要 disable 按鈕、避免重複送出。
- [ ] **只在有效時才能送出**：必填沒填/格式錯/根本沒改，就 disable 或擋下並說原因。
- [ ] **必填有標示、且與站上既有標法一致**：別這個平台紅 `*`、另一個平台寫「必填」。
- [ ] **一致性**：同功能長一樣、放同位置、用**共用元件**；同語意用同一套顏色/圖示/字。
      要加輸入欄位前先問「站上已經有這種欄位了嗎」，有就沿用、不要另造；
      **沿用之後仍要比對長相**（借來的元件自帶字體與互動態，見〈5〉）。
- [ ] **表單欄位的順序想過**：最重要的決定在上、補充性質的（備註/說明）在下；
      同一張表單裡各欄位**長相一致**，不要單獨給某一欄底色或外框。
      **新增或大改欄位：這筆資料出現的每張表單都整張重看**（見〈4〉）。
- [ ] **長文字框（備註、說明、原因、內文這類多行輸入）依內容自動撐高、不在框裡捲**：全站同一種做法——
      同一種框這頁會撐高、那頁要在框裡捲，就是不一致；適用範圍與做法屬專案設計語言（源專案 v5.38.0）。
- [ ] **視覺基本盤**：文字對比看得清、手機點擊目標夠大（約 44×44pt）、**不要只靠顏色分辨**（配文字或圖示；是非題的訊息見〈3〉：圖示＋顏色）。
- [ ] **克制**：不加沒必要的說明字、不炫技，預設乾淨。
- [ ] **清單頁有篩選的話**：現在篩了什麼**不必點就看得見**；整頁只有一顆套用鈕；
      換分頁或跳去別頁再回來條件不會被沖掉（詳見〈10〉）。
- [ ] **做完退一步，用真實寬度整頁看一次**（源專案 v4.90.0）：找「測試全綠、使用者卻一眼看得出不對」的地方——
      大片空白、撐破格線疊到隔壁、該連在一起的被換行拆開、文字被截斷；
      動到共用元件或往已經很擠的容器塞東西時，連最極端的兩頁一起看（欄位最多、最少的那兩頁，見〈1〉）。
      真實寬度：桌機畫面照桌機寬度、App 照裝置原生尺寸；縮圖只能當索引，不能當證據。

## Patterns（原則＋Do / Don't）

細則已拆成一節一檔，**都放在 `.agents/skills/ui-design/references/`（下表「讀哪份」只寫檔名，路徑都從這裡算）**。
**核心只放快篩與這張對照表；碰到下面任一情境，動手前先讀對應那一份**
（讀的是整份，不是讀表上那一句——那一句只是讓你認得出該讀哪份）。
為什麼拆（源專案 v4.97.0）：細則全塞在一檔時長到一次讀不完，另備一份濃縮版又會兩份各改各的；
拆成小核心＋一節一檔，每次啟動只付核心的份量，細則按情境讀。
別處（其他 skill、票、hook 訊息）寫的「ui-design §N」「〈克制〉」「〈示意圖〉第 13 條」這樣讀：§N 讀第 N 份（`NN-*.md`），
〈節名〉照下表找檔；內文裡的「〈5〉」「〈10〉」也是同一個意思。沒寫節名的「第 N 條」（例如別處寫的「`ui-design` 第 12 條」）
指的是〈示意圖〉的條號，讀 `mockup.md`，不是第 N 份。

| 遇到什麼 | 讀哪份 | 這份在管 |
|---|---|---|
| **畫面上要新增、改寫、或決定何時顯示任何一句字**：說明、提示、副標、ⓘ、hover 提示、placeholder、圖上的註解、空狀態以外的任何一行；動效、漸層、陰影 | `07-restraint.md`（§7 克制） | 先問「這句話在做什麼工作」，多半該刪或改介面；攔截動作、系統回報、空狀態三類必須有（源專案裡「多餘文字」是退回最大宗，**寧可多讀**） |
| **這次要改的是畫面長什麼樣**（版面、位置、大小、密度、順序、什麼跟什麼並排）：動工前先問「要不要先出圖」（第 12 條）；要出示意圖／設計圖、交圖給人拍板、原型定案要抄驗收標準 | `mockup.md`（〈示意圖〉1～13 條＋〈定案之後〉） | 改既有畫面預設做在真頁面（仍要先問，第 12 條）；圖以真頁面當底；數元件；交圖前照複雜度派 `fresh-eye-ux-auditor`（第 13 條） |

## 維護（重要：只在案主明確要求時才動）

本 skill **不自動回填**（與 `ux-writing` 同一套做法）。即使案主在對話中提了通用 UI 要求，也**先不要**改 skill。

- **只有**當案主**口頭明確說**類似「OK，我們來 review 這個對話串，討論一下有沒有值得加進（ui-design）skill 的地方」時，才啟動：
  1. 回顧該對話串，挑出案主提過的**通用**（可跨專案）UI 要求/更正。
  2. 分辨哪些是「通用原則」（→ 可進本 skill）vs「本專案主觀決定」（→ 進專案設計語言，不進本 skill）。
  3. 跟案主討論確認後，才更新 skill；框架變更記得 bump 版號＋補 `docs/FRAMEWORK.md`。
- 平時就**照現有清單套用**、不擅自擴充。
