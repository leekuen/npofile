## 目的（要解決什麼問題）

有些組織的年報、財務報告只放在臉書粉專，LK-17 的官網爬蟲刻意不碰臉書（臉書禁止未授權爬取），這些組織就一直沒有財務資料。這張票讓網站管理員**用人工的方式**把臉書粉專上的報告連結（或報告裡的數字）補進來，不寫任何去臉書自動抓資料的程式。

## 使用角色與情境

- 網站管理員：在電腦上開後台，篩出「官網填的是臉書」的組織，一家一家用自己的瀏覽器看粉專，找到年報／財報貼文或貼文裡的雲端硬碟連結，貼回後台；報告是 PDF／雲端硬碟檔就按一下讓系統讀數字，報告只是圖片就自己把數字打進「年度財務」。
- 捐款人：在前台組織頁「財務與年報」分頁看到這些報告，並看得出來源是「組織臉書粉專（管理員整理）」。

## 逼問紀錄

- 問（使用者 2026-11-27，在 LK-17）：臉書上的報告要不要收？／答：「可以先這樣，但我的確知道有些組織會放在臉書上」／因此：另開這張評估臉書的合法來源。
- 問（agent 代決，使用者偏好 agent 自己研究判斷）：能不能用臉書官方 API 自動讀別人的粉專？／答：要申請「Page Public Content Access」功能，Meta 官方文件寫明要通過 App Review（附畫面錄影與用途說明）、而且「只開放給完成企業驗證的商家」，可能還要另簽合約；企業驗證要公司或組織的登記文件，個人開發者沒有統編基本上過不了，就算過了也可能被拒／因此：這張票**不做 API**，先做人工補登；API 列為之後的選項。
- 問（agent 代決）：請組織自己登入臉書授權給我們讀它的粉專呢？／答：技術上不需要上面那個功能，但讀別人家粉專貼文的權限（pages_read_engagement 等）要給「不是 App 成員的人」用，一樣要 App Review＋企業驗證，而且要每個組織的粉專管理員願意來按授權；目前站上沒有組織帳號／因此：不在這張做，等有組織主動要求、或站方有公司／協會身分時再開票。
- 問（agent 代決）：Meta Content Library（研究用資料庫）可以嗎？／答：只給學術或以研究為主業的非營利機構研究員，資料留在 Meta 的安全研究環境，不能拿來餵公開網站／因此：不適用。
- 問（agent 代決）：人工看臉書粉專再把連結貼回來，合法嗎？／答：一個人用自己的瀏覽器看公開粉專、記下網址，是一般瀏覽行為，不是自動化爬取；我們只存「連結」和從 PDF 讀出的數字，不複製臉書上的圖片或貼文內容／因此：人工補登是目前唯一不碰邊界、馬上能做的做法。
- 問（agent 代決）：有多少組織受影響？／答：本機資料庫 100,062 個組織裡 359 個有填官網，其中 85 個被 LK-17 排除，78 個是臉書（粉專名稱網址 39、profile.php 數字 ID 21、分享短連結 9、社團 8、舊式 /pages/ 1），另有 IG 2、Google 表單類 3、格式不對 2；正式環境查不到（搬家中）／因此：一次約 80 家，人工可以做完，不值得先投資 API。
- 問：這個東西在哪一頁、給誰用？／答（agent 代決，待使用者核對）：後台組織列表多一個篩選、後台組織編輯頁的「官網報告文件」區塊（LK-17 已有）多一個來源選項，給網站管理員；前台組織頁「財務與年報」分頁（LK-17 已有）多顯示來源，給所有訪客。
- 問：誰看得到、誰看不到、誰能改？／答（agent 代決，照 LK-17 已確認的規則，待使用者核對）：後台的篩選與補登只有管理員／編輯看得到能改；前台只顯示核准上架的報告，所有人看得到。

## 需求細節

- **後台組織列表**多一個篩選「官網是社群頁（臉書／IG 等）」，用 LK-17 同一套判斷（`is_crawlable_site` 判為不可爬、但欄位有填網址的），讓管理員一次看到要人工處理的那群；列表多一欄「已補登報告數」。
- **後台組織編輯頁「官網報告文件」區塊**：管理員手動新增一筆時可選來源「組織臉書粉專（人工）」，檔案網址可以填臉書貼文網址、雲端硬碟檔案網址或 PDF 網址；存檔時自動填 `source_name`、「在哪一頁找到」填粉專網址。
- **讀數字**：手動新增的報告若網址是 PDF 或 Google 雲端硬碟檔案（LK-17 `is_document_url` 認得的），後台有一個動作「讀這份報告的數字」，沿用 LK-17 的 Claude 讀 PDF 流程，結果一樣進審核佇列等管理員核准。網址是臉書貼文（報告只是圖片）就不讀，管理員在「年度財務」區塊自己打數字（LK-17 已有，打了會鎖住）。
- **系統不會自己連到臉書**：任何 facebook.com／fb.com／instagram.com 網址只存不抓（包括讀數字、檢查連結是否還活著都不做）。
- **補官網**：如果管理員在粉專上看到組織其實有官網或雲端資料夾，可以直接把組織的「官網」欄位改成那個網址（LK-17 爬蟲下次就會去爬；改過的欄位本來就會鎖住不被覆蓋）。
- **前台**：「財務與年報」分頁的報告旁標示來源「組織臉書粉專（管理員整理）」，連結直接開原網址（新分頁）。
- 欄位權限：報告文件、年度財務沿用 LK-17（前台所有人看得到核准過的；待審核只在後台）；新的「來源」標示跟著報告一起出現，原本沒有 → 做完所有人看得到；後台篩選與「已補登報告數」只有管理員／編輯看得到。
- 誰能改：只有管理員／編輯（後台）。

## 這次可能會弄壞什麼

- W1 後台組織編輯頁：「官網報告文件」與「年度財務」區塊多了來源選項，原本爬蟲收的報告、存檔與欄位鎖定要照常。
- W2 後台組織列表：多一個篩選與一欄，原本的搜尋、其他篩選、排序要照常。
- W3 前台組織頁「財務與年報」分頁：多一個來源標示，原本官網收的報告與折線圖要照常。
- W4 LK-17 官網爬蟲：不能因為手動補了臉書網址的報告，就讓爬蟲去抓臉書。

## 驗收標準

- [ ] W2 後台組織列表選「官網是社群頁」，只出現官網是臉書／IG 等的組織，筆數與本機查詢一致；清掉篩選、原本的搜尋與排序照常。
- [ ] W1 在一家官網是臉書的組織，手動新增一筆來源「組織臉書粉專（人工）」、網址是臉書貼文的年報，存檔成功；同頁原本爬蟲收的報告沒被動到，欄位鎖定照舊。
- [ ] 新增一筆網址是 Google 雲端硬碟 PDF 的報告，按「讀這份報告的數字」，數字進審核佇列；臉書貼文網址的那筆沒有這個動作。
- [ ] W3 核准後，前台該組織「財務與年報」分頁看得到這兩份報告，旁邊標「組織臉書粉專（管理員整理）」，點了開新分頁到原網址；官網收的報告與折線圖照常。
- [ ] W4 跑一次 `crawl orgsite`，記錄裡沒有任何對 facebook.com／fb.com／instagram.com 的連線。

## 邊界（明確不做什麼）

- 不爬臉書、IG 網頁，不登入臉書，不下載臉書上的圖片或貼文內容（違反 Meta 使用條款；LK-05、LK-17 已記錄）。
- 不串 Meta Graph API（Page Public Content Access 要企業驗證＋App Review，另開票）。
- 不做「組織自己登入臉書授權粉專」，也不做組織帳號（站上目前沒有組織帳號）。
- 不做檔案上傳（管理員只貼網址；報告只是圖片時手打數字）。
- 不改 LK-17 爬蟲判斷哪些網站可爬的規則。
